2주차 스터디 시스템 기획 회의록

**이현우**
- 강사 지침 공유: 주 단위 시스템 개발 — 필수 문서(기획서·유저시나리오·시스템설계도·깃허브링크), 발표자료(PDF/PPT), 시연영상
- 제출기한: 목요일 16시까지 문서 정리해 구글드라이브 업로드 · 발표: 금요일 15시30분
- 발표 필수 목차 6개: 팀원소개·기획배경·시스템설계도·활용방안·결론·시연영상 (추가는 자유)
- **2주차 주제 = 스터디 시스템**: "다른 기술을 배우려는 의지가 있는가"를 평가하는 과제, 필수 내용은 [왜 배우고 / 무엇을 배워서 / 어떻게 활용했는지]
- 저장 방식 제안: 1주차 회의록 폴더 패턴처럼 **2주차 폴더**를 새로 만들어 같은 형식의 md로 쌓자

**김정현(진행자)**
- 시스템 골격 정의: 인풋 = 배우고 싶은 주제, 아웃풋 = 팀이 이해할 수 있는 형태
- 참고자료 형식으로 **퀴즈** 채택 → "기본설명 + 퀴즈"를 기본 베이스로 확정
- 저장 위치 후보 두 개 기각: Discord 아티팩트(권한 재설정 번거로움), 새 스레드(매번 이름-매칭 연결 번거로움)
- → **GitHub 2주차 폴더**에 md로 쌓는 방식 채택 (어디서 불러도 동일 적용)
- 명령 형태 초안 제시: `/알려주기 {주제} {이유} {활용처}`
- TCP/UDP 관련 내용은 "맥락 오염" 우려로 이 채널이 아닌 다른 곳에서 다루기로 함

**박진**
- 이유(reason) 예시 제안: "웹소켓, 팀프로젝트에 필요해서 배우고 프로젝트에 활용했다"는 식의 서술
- GitHub 폴더 저장 방식에 동의

**유민성**
- 참고자료 형식으로 퀴즈 제안
- 활용처 근거에 **TCP/UDP** 언급 포함 요청 · "우리 프로젝트는 TCP만 사용" 확인
- 자신들 README의 설계원칙(서버가 유일한 진실 공급원·상태 전체 브로드캐스트·타이머 기반 실시간 진행)을 근거로 웹소켓이 왜 필요했는지 상세 설명 — 이게 [활용처] 답변의 실제 콘텐츠로 채택됨

---
**결론**: 2주차 "스터디 시스템" 과제용으로, `주제+이유+활용처` 3개 인자를 받아 기본설명+퀴즈를 생성하고 **GitHub 2주차 폴더**에 1주차 회의록과 같은 패턴의 md로 저장하는 기능(`/알려주기` 가칭)을 만들기로 합의. 첫 주제는 웹소켓, 활용처 근거는 유민성이 제시한 README 설계원칙. TCP/UDP는 별도 채널에서 다룰 예정.

## 기획서는 이렇게 쓰려고 해요

이 논의 내용을 그대로 기획서 뼈대로 옮길게요.

1. **기획 배경** — 강사 요구사항("다른 기술을 배우려는 의지가 있는가" 평가) 그대로 인용, 왜 이걸 도구화하려는지(매번 수작업으로 정리하지 않기 위함)
2. **핵심 컨셉** — 인풋 `{주제} {이유} {활용처}` 3요소 → 아웃풋 `기본설명 + 퀴즈`. 이유·활용처를 강제로 받는 이유(그냥 챗봇 질문과 구분하려는 목적, 김정현이 짚은 포인트)를 명시
3. **명령 인터페이스** — `/알려주기 {주제} {이유} {활용처}` 형태, 기존 `channel-summarize`·`meeting-minutes` 스킬과 동일한 계열로 소개
4. **저장/배포 방식** — GitHub `2주차/` 폴더에 `1주차` 회의록과 동일한 명명 패턴으로 md 저장. 왜 아티팩트·스레드가 아니라 이 방식인지(권한/매칭 번거로움) 기각 사유까지 같이 적어서 "설계 결정에 근거가 있다"는 걸 보여줄게요
5. **예시 케이스(첫 실행 결과)** — 주제=웹소켓, 이유=팀프로젝트에 필요해서, 활용처=유민성이 정리한 README 설계원칙(서버 권위 상태·전체 브로드캐스트·타이머 기반 실시간)을 그대로 활용
6. **확장 여지** — 팀 자체 로그(예: 유민성-logs)를 선택적으로 참고 소스로 넣는 옵션은 미착수로 명시

TCP/UDP는 말씀하신 대로 여기 기획서엔 안 넣고 다른 채널에서 따로 처리할게요.
