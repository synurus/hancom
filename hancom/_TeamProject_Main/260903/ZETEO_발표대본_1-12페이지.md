# **ZETEO 최종발표 — 발표 대본 (1\~12쪽)**



## **1쪽 · 표지 — 0:15**

안녕하세요.

라이어 게임 속에 숨어있는 하나의 봇을 찾는 프로젝트.

ZETEO의 발표를 맡은 이현우 입니다.

잘 부탁 드립니다.



## **2쪽 · 발표 흐름 — 0:12**

발표순서는 이렇습니다.

중간의 코드 리뷰가 오늘 발표의 핵심이고,

마지막에 하이라이트로 시연을 진행하겠습니다.



## **3쪽 · 팀원 소개 — 0:25**

팀원을 소개하겠습니다.

먼저 팀장 박진은,

팀장으로서 프로젝트를 지휘했고,

디자인 토큰과 공용 컴포넌트,

그리고 플레이화면을 제외한 나머지 화면을 제작하였습니다.

그리고 저 이현우는,

컨텐츠 기획 및 게임 플레이 화면을 구현했습니다.

다음 유민성 팀원은

서버와 DB쪽을 담당했는데,

서버의 데이터를 필터링해서 전달하는,

정보 격리 작업을 중점으로 뽑을 수 있습니다.

마지막 김정현 팀원은

봇 엔진을 담당했습니다.

봇의 말투와 행동 규칙,

그리고 프롬프트를 개선하는 루프를 설계하였습니다.



## **4쪽 · 기획 배경 — 0:50**

저희 프로젝트의 출발은 인터넷에서 본 글이었습니다.

"AI와 마피아게임을 하면 티나는 이유" 라는 제목이었고,

봇이 말하는 메시지에 더해서 발언 타이밍이나 맥락에서 티가 난다는 내용이었습니다.

그때 "원인을 알면 고쳐볼 수 있겠다" 생각이 들었고,

저희 프로젝트가 시작했습니다.



저희는 라이어게임 속에 봇을 찾는 게임을 담고,

그 결과와 피드백을 통해

프롬프트를 개선하는 시스템을 만들었습니다..



## **5쪽 · 유저 시나리오 — 0:25**

유저 시나리오는 일반적인 라이어 게임과 동일 합니다.

추가로 게임 종료시에 봇이라고 추정되는 플레이어를 지목하고,

결과화면에서 게임결과 봇지목 결과를 확인합니다.

그리고 설문에서 봇을 지목한 이유를 수집합니다.



## **6쪽 · 시스템 설계도 — 0:35**

다음은 시스템 설계도 입니다.

브라우저에서 유저가 행동하면,

서버 로직에서 처리한뒤에,

서버가 보낸 게임 상태를 그리기만 합니다.

이때 민감한 정보를 필터링하게 됩니다.

그리고 저희프로젝트의 핵심,

프롬프트를 개선은 봇모듈에 적용됩니다.





\[부록]

\[민성이 멘트]

"event로 클라이언트에 전송할 때 봇 식별자 같은 민감 정보가 그대로 실리지 않도록, 서버에서 역할별로 필터링해서 내보내는 방식으로 설계했습니다."

────────────────────────────────────────────────

\[삭제한 부분]

브라우저							화면 6개  ·  상태 1개

action							참가/발언/투표

event								GameState 전체

Express + Socket.IO					단일 프로세스 · 단일 포트

Express + Socket.IO -> 게임 로직 코어		요청 처리

게임 로직 코어 -> 봇 모듈				봇 차례마다

index.ts							차례판단

prompts.ts							루프가 고치는 곳

llm.ts								generate()

PostgreSQL							games — bot\_commit\_sha · bot\_provider · bot\_model

Discord Webhook					게임 종료 시 · 알림만

LLM 호환 API						봇 차례마다 generate()



## **7쪽 · 코드 리뷰 · 기획 — 0:35**

이제부터 저희 프로젝트의 핵심,

봇을 개선하는 시스템에 대해 설명하겠습니다.

처음에는 관전자 봇이 플레이어봇을 채점하는 방식을 생각했습니다.

기획이 구체화됬을때는 설문을 받고 봇이 자동으로 반영하는 방식을 생각했고,

구현까지 해봤습니다.

개선 시스템이 완성되기 전 MVP에서는,

수동으로 설문을 검토하고 수정하는 방식을 사용했습니다.

그런데 3가지 방법 모두 문제가 있었습니다.



## **8쪽 · 코드 리뷰 · 맥락 — 0:35**

지금부터 저희가 완성한 봇 개선 시스템을 설명하겠습니다.

먼저 게임 한판이 끝나면 게임결과, 채팅로그, 투표와 설문 내용을 종합합니다.

가장 중요한 건 설문 단계에서 봇이라고 판단한 핵심발언을 선택하는 부분입니다.



## **9쪽 · 코드 리뷰 · 선택과 근거 — 0:42**

기록이 다섯 판 쌓이면 루프가 돌아갑니다.

먼저 봇이라 판단한 장면들을 확인하고,

반복 측정으로 기준을 정합니다.

봇 지침을 수정한 후에,

동일 상황에서 재측정을하고,

설문 문항을 갱신합니다.

그리고 자동으로 Pull Request를 올리면,

사람이 검토하고 승인합니다.



## **10쪽 · 코드 리뷰 · 효과 — 0:38**

종합하면,

게임을 플레이하면,

기록이 쌓이고,

5판이 쌓이면 봇 개선 루프가 작동합니다.

그리고 지침과 설문이 바뀐채로,

다음 게임이 시작됩니다.

이렇게 봇을 개선하는 시스템이 저희 프로젝트의 핵심입니다.



## **11쪽 · 활용 방안 — 0:28**

다음은 활용방안입니다.

저희 프로젝트는 봇의 두뇌만 갈아끼울 수 있고,

그대로 벤치마크로 활용할 수 있습니다.

실제로 저희가 개발중에,

ChatGPT와 알리바바 API를 바꿔가면서 테스트를 진행하였고,

그 결과 유의미한 성능 차이를 확인할 수 있었습니다.



## **12쪽 · 사업성 — 0:28**

사업성입니다.

지금 단계에서 실행 가능한 수단은 애드센스입니다.

게임에 몰입하는걸 깨지 않기위해,

게임화면을 제외한 다른화면에 들어갑니다.

목적은 큰 수익이 보다는 서버 유지비 충당입니다.

부수적으로는 영어 버전 동시 런칭을 통해서,

글로벌 시장을 겨냥할 수 있습니다.

현지화 비용이 낮기 때문에 언어만 추가하면 가능한 방법입니다.
