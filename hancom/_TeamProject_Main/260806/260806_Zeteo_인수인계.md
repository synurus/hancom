### 🎉 실 서버 연동 배선 + 라이브 스모크 테스트 (8/6, 이 세션)

`App.tsx`(파트 D 소유)가 이제 mock이 아니라 `useGameState()`를 직접 마운트한다. `?mock=`
쿼리가 있을 때만 `MockHarness.tsx`가 대신 뜨는 구조로 분리돼 있다 — 즉 **인수인계 §9의
"서버가 dev에 오면 할 일" 체크리스트가 지금 실행 가능한 상태**다.

이 세션에서 backend(`npm run dev -w backend`)+frontend(`npm run dev -w frontend`)를 실제로
띄우고 Playwright로 4개 브라우저 탭(사람 4명)이 같은 방번호로 입장하는 걸 재현했다
(서버가 5번째 자리에 `테스트봇`을 자동 배정 — `BOT_API_KEY`는 팀 전용이라 이 세션엔 없음).

**확인된 것:**

1. **join→lobby→roleReveal→describe, mock 없이 실제 소켓으로 전환 확인.** 전원 준비완료 →
   `MIN_PLAYERS_TO_START=5` 충족 → roleReveal 진입 → 5초 타이머 만료 → describe 진입, 전부
   실측(코드 읽기가 아니라 실행 결과).
2. **라벨 형식 A~Z가 실제 GameState에 반영돼 있음을 실측.** 서버가 `B`·`U`·`K`·`N`·`O` 같은
   단일 알파벳 라벨을 실제로 내려보냄.
3. **정보 유출 0건 — 웹소켓 raw payload 레벨로 확인.** 프론트가 화면에 그리는 걸 보는 게
   아니라 웹소켓 프레임을 직접 가로채 4명 전원이 받는 raw `GameState`를 검사 — `role`
   (다른 사람 것)·`isBot` 필드가 **payload 자체에 존재하지 않음**(타입에 없어서 애초에
   못 새는 구조, 12절 ② 참조). `word`는 시민 전원에게 정상 공개, 라이어에게만 `null`인
   것도 확인.
4. **봇 API 키 없이도 서버가 안 죽는다.** 봇 차례에서 `decideBotAction` 실패(`BOT_API_KEY`
   없음) → 로그만 찍고 서버 계속 진행. `index.ts`의 "실패해도 phase 타이머가 이어받는다"는
   주석 그대로 동작함을 실측.
5. `Timer.tsx`의 `deadlineAt - now` 매틱 재계산, `stateMachine.ts`의 `round` 증가 로직은
   코드로 재확인(라이브로는 debate·lifeVote의 60초 타이머까지는 시간상 안 감).

**아직 못 본 것 — 팀 API 키가 있는 로컬 환경 필요:**

**예상한 파일 수·줄 수와 다르면 커밋하지 말고 원인부터 찾는다.**
`git add -A` 보다 파일을 직접 지정하는 편이 낫다.

### 시험 병합 — 남의 브랜치를 미리 확인하는 법

```bash
git checkout -b trial origin/feat/game-ui
git merge --no-commit --no-ff origin/feat/server

git diff --cached --diff-filter=D --name-only   # ★ 조용히 삭제되는 파일
git diff --name-only --diff-filter=U            #   충돌로 뜨는 파일
npm run build -w frontend

git merge --abort
```

**`--diff-filter=D` 를 꼭 본다.** 삭제는 대부분 충돌로 안 뜬다 — 내가 고친 파일만 git이 묻고,
안 건드린 파일은 묻지 않고 삭제를 적용한다. R8에서 27개 중 24개가 그랬다.
이 절차로 R5·R8·`name→label`·`revealedBotId` 를 전부 병합 전에 찾았다.

### 병합했는데 커밋 안 된 상태로 남을 수 있다 — 검증법

우선순위: **먼저 커밋, 그다음 `git merge`.** 관리자 가이드가 원래 이 순서였고, 실측으로도 맞았다.
미커밋 파일이 있는 채로 `git merge`를 돌리면 그 파일이 병합 대상과 겹칠 때
`error: Your local changes ... would be overwritten by merge` 로 아예 시작도 안 한다.

병합이 끝난 뒤엔 **정말 병합됐는지 확인**한다. `git show --stat HEAD` 에 `Merge:` 줄이 없으면
그건 병합 커밋이 아니라 그냥 일반 커밋이다 — 어디선가 다른 방식(예: 특정 파일만
`git checkout <branch> -- <path>`)으로 내용만 들어온 것일 수 있다. 더 확실한 방법:

```bash
git merge-base --is-ancestor origin/dev HEAD
echo $LASTEXITCODE   # 0 = 정말 병합됨, 그 외 = 아니다
```

이 명령으로 "커밋에 shared-types 24줄이 들어있긴 한데 실제로 dev가 병합된 게 맞나?"를
확실히 판별했다. 아무것도 안 지워지지 않은 상태(push 전)라 `git reset --soft HEAD~1` 로
안전하게 되돌리고 다시 했다 — **push 전이면 되돌리는 데 위험이 없다.**

### 남의 브랜치 파일을 잠깐 빌려 쓰고 되돌리기 — 함정 하나

로컬 백엔드를 돌려보려고 `git checkout origin/feat/server -- apps/backend` 로 파일만 가져온 적이 있다
(커밋은 안 함 — 백엔드는 우리 소유가 아니라서). 되돌릴 땐:

```bash
git checkout HEAD -- apps/backend
```

이걸로 **기존에 있던 파일들**은 원상복구되지만, **HEAD에 없던 새 파일**(`feat/server`에만 있던
`bot/scheduler.ts`·`bot/transcript.ts`)은 안 지워지고 "new file" 로 스테이징된 채 남는다.
`checkout <commit> -- <path>` 는 `<commit>`에 있는 파일만 되돌리지, 없는 파일을 지우지는 않는다.

```bash
git restore --staged apps/backend/src/bot/scheduler.ts apps/backend/src/bot/transcript.ts
rm apps/backend/src/bot/scheduler.ts apps/backend/src/bot/transcript.ts   # PowerShell: Remove-Item
git status   # "nothing to commit, working tree clean" 이어야 끝
```

**이 패턴 자체는 재사용 가치가 있다.** 로컬에서 최신 백엔드로 프론트를 붙여보고 싶을 때,
브랜치를 통째로 merge하지 않고 `apps/backend` 디렉터리만 빌려서 테스트하고 위 순서로 되돌리면
`feat/game-ui` 히스토리를 전혀 더럽히지 않는다. 단, `feat/server` 에 `apps/frontend` 삭제(R8)나
봇 코드 이슈(R5)가 섞여 있으니 **`apps/frontend` 는 절대 이 방식으로 가져오지 않는다.**

### 푸시된 커밋을 되돌려야 할 때

`git revert` **도 커밋을 하나 더 만든다.** 커밋 없이 없애려면 `reset --hard` + `push --force` 뿐이다.

| 상황 | 방법 |
| --- | --- |
| 혼자 쓰는 브랜치, 아직 아무도 안 봄 | `git reset --hard <이전>` + `git push --force` |
| **PR이 열려 있거나 남이 볼 수 있음** | **새 커밋으로 되돌린다** |

PR에는 "두 커밋이 상쇄되며 순변화는 X뿐"을 확인 명령과 함께 남긴다.

### 줄바꿈(CRLF/LF) — 해결됨

| 증상 | `.gitattributes` 를 pull 했는데도 `npm run format` 후 40개 파일이 modified |
| --- | --- |
| 원인 | `git pull` 은 **이미 디스크에 있는 파일을 다시 깔지 않는다** |
| 진단 | `git ls-files --eol <파일>` → `i/` `w/` `attr/` 비교 |
| 해결 | `git restore .` **미커밋 작업이 있으면 commit/stash 먼저** |
| 아님 | `git add --renormalize .` 는 **필요 없었다.** blob이 원래 LF였다 |

### 푸시가 안 될 때

`Could not resolve host: github.com` — **DNS 문제이고 git 문제가 아니다.**

| 확인 | 의미 |
| --- | --- |
| `ping 1.1.1.1` 성공 | 회선은 살아 있다 |
| `nslookup github.com 1.1.1.1` 성공 | 네트워크로 나가는 질의는 정상 |
| `Resolve-DnsName github.com` 실패 | Windows DNS 클라이언트 계층 문제 |

`Set-DnsClientServerAddress -InterfaceAlias "이더넷" -ResetServerAddresses` 로 풀렸다.
**수동으로 박기 전에 자동으로 되돌리는 것부터.**

### 자잘한 것

- `git fetch` 는 받아올 게 있을 때만 출력한다. **조용한 게 정상**
- `git rev-parse --short` 는 리비전을 **하나만** 받는다. 여러 개면 `git branch -avv`

### 삭제는 충돌로 뜨지 않는다

R8에서 `feat/server` 가 `apps/frontend` 27개를 제거했는데, 병합해보니 **충돌은 3개뿐**이었다.

**→ `git diff --cached --diff-filter=D` 를 반드시 본다.** 이게 없었으면 못 봤다.

### 의도된 것과 잘못된 것을 구분한다 — 다만 결과는 따로 본다

R8은 **관리자가 백엔드 정리를 위해 의도한 삭제**였다. 내가 처음에 "사고"로 단정한 건 틀렸다.

merge-base에 파일이 있는 이상 git은 "삭제한 브랜치"로 읽어 병합에 전파한다.

**→ "이건 실수 같은데요"가 아니라 "의도는 알겠는데 병합하면 이렇게 됩니다"로 말한다.**
전자는 상대를 방어적으로 만들고, 후자는 같이 볼 사실을 준다.
그리고 목적이 "작업 폴더에서 안 보이게"라면 `git sparse-checkout` 이 저장소 영향 없이 같은 일을 한다.

### "커밋됐다"와 "병합됐다"는 다른 말이다

`git commit` 로그에 shared-types 24줄이 찍혀 있어서 병합된 줄 알았는데, `git show --stat` 에
`Merge:` 줄이 없었다 — 부모가 하나뿐인 평범한 커밋이었다. 어디선가 파일 내용만 들어온 것이지
실제 dev 히스토리가 편입된 게 아니었다. `git merge-base --is-ancestor <branch> HEAD` 로 exit code를
확인하고 나서야 확실해졌다.

**→ diff·stat만으로 "병합됐다"고 판단하지 않는다.** 특히 필수 필드가 계속 추가되는 계약처럼,
내용이 우연히도 맞아떨어질 수 있는 상황에서는 ancestry를 직접 확인한다.

### 남의 브랜치가 통째로 자라난 파일은 패치가 아니라 교체로 받는다

`feat/server` 의 계약 대응 커밋(`cd1c6e0`)이 `room.ts` 136줄·`index.ts` 193줄을 바꿨다.
우리 로컬 버전은 그 파일들의 스켈레톤(`e887783` 시점)이라, 이 패치를 그 위에 얹으려 하면
베이스가 달라 안 먹힌다. **원본 구현 자체가 다른 브랜치에서 처음부터 자라난 파일은,
diff를 얹지 말고 파일 단위로 최신본을 통째로 가져온다** (단, 우리가 그 파일의 소유자가 아닐 때는
커밋하지 않고 로컬 테스트용으로만 — 위 8절 참조).

- `GameState`는 매번 통째로 온다 — 증분 반영 로직이 없다 (`setState(e.state)` 한 줄)
- 타이머는 `deadlineAt`(절대 시각)만 받아 매 틱 `deadlineAt - Date.now()`로 재계산한다
- 과반·투표자 수는 전부 `players.length`에서 계산한다 — 인원수 하드코딩 없음
- `isBot`·`role`은 애초에 `GameState`에 없다 — 서버 `view.ts`가 한 곳에서 걸러 보낸다

## 12. 핵심 코드 리뷰

> 발표용 구조(맥락/문제 → 대안 → 선택+근거 → 효과)로 정리. 근거 상세는 4절 "확정된 설계 결정"과
> 대응한다 — 발표 스크립트를 쓸 때는 이 절을, 근거를 다시 찾을 때는 4절을 본다.

### ① `myId` 필드 발견 — 계약의 명백한 누락을 화면을 그리다 찾아냄

- **맥락/문제**: `GameState`에 "지금 내 차례인가"를 판단할 방법이 없었다. v1.0 계약엔
  `myId` 필드 자체가 없었고, `ServerEvent`도 `state`/`error` 둘뿐이라 join 응답으로도
  받을 수 없었다. 이 상태로는 묘사 화면의 입력 잠금과 생사 투표의 투표자/지목자 분기가
  통째로 막힌다.
- **대안**: (a) 소켓 join 응답에 별도 필드로 실어 보낸다 — 이벤트 종류가 하나 늘고 화면이
  `state` 외의 또 다른 소스를 신뢰해야 한다. (b) `GameState`에 필드로 얹는다 — "상태는
  항상 통째로 온다"는 설계원칙과 맞는다.
- **선택 + 근거**: (b) 채택. 서버가 단일 진실 공급원이라는 원칙을 지키려면 클라이언트가
  신뢰하는 소스는 `GameState` 하나여야 한다. join 응답에 실으면 이벤트를 놓쳤을 때 복구
  경로가 따로 필요해진다.
- **효과**: `myId`를 포함해 화면을 그리다 발견한 필드가 ★1~★6, 총 6개 — v2.0 계약의
  `GameState` 신규 필드 대부분이 이 경로로 나왔다. "타입만 보고 먼저 만들어보면 계약의
  구멍이 보인다"는 이 팀의 협업 방식 자체를 증명한 사례.

### ② 라벨 익명화 — 서버 한 곳에서 막지 않으면 어디서든 샌다

- **맥락/문제**: `PublicPlayer.name`이 `label`("참가자 N")로 바뀐 건 봇 판별에 아이디가
  단서가 되지 않게 하려는 의도된 결정이었다. 그런데 `view.ts`는 `label`만 내보내도록
  게이팅돼 있었지만, `stateMachine.ts`가 시스템 메시지 문장을 만들 때는 여전히 실명을
  쓰고 있었다 — 지목이 일어날 때마다 실명이 로그로 새는 구멍이었다.
- **대안**: (a) 화면(C) 쪽에서 문장에 실명이 섞여 오면 걸러낸다 — 어떤 문자열이 이름인지
  화면이 판단해야 해서 취약하다. (b) 익명화 책임을 지닌 `view.ts` 한 곳으로 모든 출구를
  통일한다.
- **선택 + 근거**: (b). "상태 출구가 `buildGameStateFor` 한 곳으로 모여 있다"는 원칙을
  실제로 지키려면, 문장을 생성하는 지점(`stateMachine.ts`)도 그 원칙의 적용 범위 안에
  있어야 한다. 규칙을 정했으면 그 규칙이 닿지 않는 곳이 있는지 확인하는 문제였다.
- **효과**: `stateMachine.ts`가 `.label`을 쓰도록 수정되며 유출 경로가 막혔다. 이후
  `reasons`(설문)·`revealedBotId` 등 신규 필드도 같은 게이팅 패턴(result 이전엔 빈 값)을
  그대로 따라가는 선례가 됐다.

### ③ ★7(`returnReason` 필드) 기각 — 필드로 못 담는 정보는 필드로 만들지 않는다

- **맥락/문제**: 동점 재투표와 "살린다" 판정 복귀, 둘 다 `phase`가 `debate`로 되돌아오는
  같은 모양이라 화면이 "왜 돌아왔는지" 구분할 방법이 필요했다.
- **대안**: (a) `returnReason: 'tie' | 'spared'` 같은 필드를 계약에 추가한다. (b) 서버가
  시스템 메시지 문장으로 사유를 내려보내고 화면은 문장을 그대로 표시만 한다.
- **선택 + 근거**: (b) 채택, (a) 기각. 필드로 만들면 "동점입니다" 같은 카피를 화면이
  하드코딩해야 하고, "참가자 7님이 살아남았습니다"처럼 **대상이 들어간 문장은 애초에
  필드로 표현이 안 된다.** `round`(상태: 지금 몇 번째)와 시스템 메시지(사건: 왜
  돌아왔는가)는 서로 대체 관계가 아니라는 게 핵심이었다.
- **효과**: 계약에 필드 하나가 안 늘었고, 두 복귀 경로의 **화면 구조가 완전히 동일**해져서
  컴포넌트 분기가 필요 없어졌다. 반대급부로 화면 쪽에서 "구조가 같다"는 전제를 스크린샷
  비교 같은 방식으로 검증하려 하면 안 된다는 게 배운 점(10절 참조) — 플레이어는 한쪽
  경로만 겪는다.

### ④ `Reveal`의 `liarGameResult` 항상 `null` — 결과 은닉도 스포일러가 될 수 있다

- **맥락/문제**: 라이어가 적발됐는지, 시민이 오인 처형됐는지를 `reveal` 단계에서 알려줄지
  결정해야 했다.
- **대안**: (a) 승패가 이미 정해졌다면 `reveal`에서도 `liarGameResult`를 채워 보여준다.
  (b) 두 경우 모두 `null`로 두고 `result` 단계까지 미룬다.
- **선택 + 근거**: (b) 채택. 라이어가 적발된 경우만 `reveal`에서 결과를 숨기면, **"결과가
  안 뜬다"는 사실 자체가 라이어였다는 스포일러**가 된다. 두 경우를 화면에서 구분할 수
  없게 만들려면 항상 미뤄야 했다.
- **효과**: `Reveal.tsx`의 승패 조건부 블록은 코드에 남겨두되(`liarGameResult`가 `null`이면
  자연히 안 뜬다) 지우지 않는 선택으로 이어졌다. 서버도 `pendingLiarGameResult`에 값을
  예약해뒀다가 `botVote → result` 전이에서만 옮기고, `view.ts`가 한 번 더 `null`로 감싸는
  이중 방어 구조로 구현됐다 — 화면·서버 양쪽에서 같은 원칙을 지키는 사례.
