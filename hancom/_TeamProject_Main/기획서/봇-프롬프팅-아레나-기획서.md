# 봇 프롬프팅 아레나 (Bot Prompting Arena)

> 코드가 아니라 **프롬프트로 봇을 만들어** 서로 겨루게 하는 웹 플랫폼

- **작성일**: 2026-07-29
- **기간**: 4주 (2026-07-27 ~ 2026-08-21 개발 / 09-08 발표)
- **인원**: 4명
- **분류**: 프론트엔드 팀 프로젝트

---

## 1. 한 줄 정의

사용자가 자연어로 전략을 쓰면, 시스템이 그것을 **검증된 규칙 집합으로 컴파일**하고, 컴파일된 봇들이 결정론적 시뮬레이션 안에서 대전해 리그 순위를 겨루는 플랫폼.

## 2. 기획 배경

"프롬프트를 잘 쓴다"는 말이 실력으로 인정받는 시대가 됐지만, 그것을 **객관적으로 측정하는 방법**은 없다. 이 프로젝트는 프롬프트의 품질을 승률이라는 숫자로 환산할 수 있는 환경을 만든다.

기존 봇 프로그래밍 대회(Battlesnake, CodinGame, Coder One 등)는 참가자가 코드를 작성해야 하므로 진입장벽이 높다. 프롬프트로 대체하면 **누구나 30초 안에 참전**할 수 있으면서도, 플랫폼의 기술적 난이도는 그대로 유지된다.

## 3. 핵심 설계 원칙

> **LLM은 컴파일러다. 심판이 아니다.**

이 원칙이 프로젝트 전체를 관통한다.

| 구분 | LLM 개입 여부 |
|---|---|
| 봇 등록 (프롬프트 → 규칙 변환) | **개입함** — 1회 |
| 대전 시뮬레이션 | 개입 안 함 |
| 리그 수천 판 자동 대전 | 개입 안 함 |
| 리플레이 재생 | 개입 안 함 |

**따라오는 이점**

- 대전이 **결정론적** → 같은 봇·같은 시드면 항상 같은 결과 → 리플레이가 입력 로그만으로 성립
- 대전이 **무료·즉시** → 리그 수천 판을 부담 없이 돌림
- 대전이 **검증 가능** → 컴파일된 규칙을 사람이 읽고 이해할 수 있음
- LLM 서비스가 죽어도 **기존 봇들의 리그는 계속 돌아감**

## 4. 아키텍처

```
[자연어 프롬프트]
       │
       ▼
[컴파일 파이프라인]  ← LLM (온도 0, 버전 고정)
       │
       ▼
[JSON 규칙 DSL]  ──▶ 스키마 검증 ──실패──▶ 오류를 다시 LLM에 (최대 2회)
       │                                          │
       │                                       실패 지속
       │                                          ▼
       │                                    [기본 봇으로 폴백 + 사용자에게 안내]
       ▼
[규칙 인터프리터]
       │
       ▼
[결정론 게임 엔진] ──▶ [입력 로그] ──▶ [리플레이 뷰어]
       │
       ▼
[리그 러너 / Elo] ──▶ [리더보드]
```

**중요**: 게임 엔진은 순수 TypeScript 함수로 작성해 **브라우저와 서버 양쪽에서 동일하게 실행**되게 한다. 이것 자체가 결정론의 증명이 되고, 리그는 서버에서 대량으로, 개별 대전은 클라이언트에서 즉시 돌릴 수 있다.

## 5. 게임 베이스: 행성 정복

### 선정 이유

| 조건 | 충족 |
|---|---|
| 프롬프트로 표현할 전략 공간이 넓은가 | 공격 대상 선정 / 병력 배분 / 방어 판단 / 타이밍 |
| 우선순위 규칙 목록으로 표현되는가 | 자연스럽게 떨어짐 |
| 관전이 재밌는가 | 함대 이동과 숫자 변화가 그림이 됨 |
| 구현이 가벼운가 | 격자 없이 좌표와 거리만 |
| 초보 봇과 좋은 봇의 차이가 보이는가 | 명확 |

### 규칙 명세

- **맵**: 15~23개 행성. 2차원 좌표. 좌우 대칭 배치(공정성 필수)
- **행성 속성**: 소유자(중립 / P1 / P2), 병력 수, 생산력(1~5)
- **매 턴 처리 순서** (이 순서가 결정론의 핵심, 고정할 것)
  1. 각 봇의 규칙 평가 → 함대 발사 명령 수집
  2. 함대 발사 (출발 행성에서 병력 차감)
  3. 이동 중 함대 1턴 전진
  4. 도착 함대 처리 — 같은 편이면 합류, 다른 편이면 전투(많은 쪽 승, 차이만큼 잔존)
  5. 소유 행성 병력 += 생산력 (중립 행성은 증가 없음)
- **함대 도착 시간**: `ceil(유클리드 거리)` 턴
- **승리 조건**: 상대의 행성과 함대가 모두 소멸, 또는 200턴 경과 시 총 병력이 많은 쪽
- **턴 제한**: 200

### 대안 게임

DSL 표현력 검증에 실패할 경우를 대비한 후보.

- **격자 폭탄 게임(봄버맨)** — "막다른 길에서는 폭탄을 놓지 않는다" 같은 규칙이 자연어로 매우 직관적
- **부분관측 탱크** — "적을 마지막으로 본 방향으로 추격" 같은 기억 기반 규칙

## 6. 봇 DSL 명세

### 형태

우선순위가 매겨진 **조건-대상-행동** 규칙 목록. 매 턴 우선순위 순으로 평가하며, 각 출발 행성은 한 턴에 최대 1개 행동을 수행한다.

```json
{
  "name": "확장 우선형",
  "rules": [
    {
      "priority": 1,
      "when": { "fact": "incoming_enemy_fleet", "op": ">", "value": 0 },
      "from": { "select": "my_planets", "filter": "nearest_to_threat", "limit": 1 },
      "to":   { "select": "my_planets", "filter": "under_threat", "limit": 1 },
      "action": { "type": "reinforce", "amount": "just_enough" }
    },
    {
      "priority": 2,
      "when": { "fact": "turn", "op": "<", "value": 30 },
      "from": { "select": "my_planets", "filter": "strongest", "limit": 2 },
      "to":   { "select": "neutral_planets", "filter": "highest_growth", "limit": 1 },
      "action": { "type": "attack", "amount": "just_enough_plus", "value": 3 }
    },
    {
      "priority": 3,
      "when": { "fact": "always" },
      "from": { "select": "my_planets", "filter": "strongest", "limit": 1 },
      "to":   { "select": "enemy_planets", "filter": "weakest", "limit": 1 },
      "action": { "type": "attack", "amount": "half" }
    }
  ],
  "fallback": { "action": "hold" }
}
```

### 어휘 (v1 기준 — 1주차 검증 후 조정)

| 항목 | 값 |
|---|---|
| `when.fact` | `always`, `turn`, `my_total_ships`, `enemy_total_ships`, `my_planet_count`, `incoming_enemy_fleet`, `ship_advantage_ratio` |
| `select` | `my_planets`, `enemy_planets`, `neutral_planets` |
| `filter` | `weakest`, `strongest`, `closest`, `farthest`, `highest_growth`, `best_value`, `under_threat`, `nearest_to_threat` |
| `action.type` | `attack`, `reinforce`, `hold` |
| `action.amount` | `all`, `half`, `just_enough`, `just_enough_plus`, `fixed` |

### 제약 (공정성)

- 규칙 개수 상한: **12개**
- 프롬프트 길이 상한: **1,000자**
- 컴파일 모델·버전·온도(0) 고정 — 모델이 바뀌면 기존 리더보드는 별도 시즌으로 분리

### 직접 편집 모드

컴파일된 DSL을 사용자가 **직접 수정할 수 있게** 한다. 이것은 편의 기능이 아니라 **"LLM 없이도 이 플랫폼이 성립한다"는 증명**이며, "GPT 래퍼" 비판에 대한 가장 강력한 반박이다.

## 7. 컴파일 파이프라인

1. **시스템 프롬프트**: DSL 스키마 전문 + 어휘 목록 + 출력은 JSON만 + 예시 3개
2. **사용자 프롬프트는 데이터로만 취급** — 지시로 해석하지 않음
3. **1차 검증**: JSON 파싱 → 스키마 검증(zod)
4. **2차 검증(의미)**: 알 수 없는 어휘 사용, 규칙 0개, 도달 불가능한 규칙, 우선순위 중복
5. **자가 수정 루프**: 검증 오류 메시지를 그대로 LLM에 반환해 재생성 — **최대 2회**
6. **최종 실패 시**: 기본 봇으로 폴백하고, 사용자에게 어느 표현이 해석되지 않았는지 안내
7. **캐싱**: 동일 프롬프트 해시는 재컴파일하지 않음

### 프롬프트 주입 방어

게임 결과에 영향을 주는 것은 **오직 스키마 검증을 통과한 DSL뿐**이다. LLM이 무엇을 출력하든 게임 엔진은 DSL만 읽으므로, 주입 시도는 검증 단계에서 자동으로 걸러진다. 이것은 사후 필터링이 아니라 **구조적 방어**이며, 발표에서 강조할 지점이다.

## 8. 화면 구성

### 8.1 프롬프트 에디터 (좌우 분할)

- 좌: 자연어 입력 + 예시 프롬프트 제공
- 우: 컴파일된 규칙을 **카드 형태**로 표시. 우선순위 순 정렬
- 자연어 문장과 생성된 규칙 카드를 **하이라이트로 연결** — 어떤 문장이 어떤 규칙이 됐는지
- 컴파일 실패 시 해석되지 않은 표현 표시

### 8.2 대전 화면

- 행성 맵 렌더링, 함대 이동 애니메이션
- 재생 / 일시정지 / 배속 / 턴 이동
- **규칙 발동 하이라이트** — 매 턴 어떤 규칙이 발동했는지 사이드바에 표시

> 이 기능이 프로젝트의 심장이다. "내가 쓴 이 문장이 이 행동을 낳았다"가 눈에 보이는 순간이 다른 어떤 봇 아레나에도 없는 장면이다. 우선순위 최상.

### 8.3 리플레이 뷰어

- 타임라인 스크럽
- 턴별 병력 추이 그래프
- 봇별 규칙 발동 통계 (어떤 규칙이 몇 번 발동했는가 → 죽은 규칙 발견)

### 8.4 리더보드 / 리그

- Elo 순위, 전적, 봇의 프롬프트 공개 여부 선택
- 100판 자동 대전 후 승률 통계

### 8.5 봇 상세

- 프롬프트 버전 이력 및 diff
- 버전별 Elo 변화 그래프 — **프롬프트를 고쳤더니 순위가 올랐다**를 보여주는 화면

| 3 | 컴파일 실패율 높음 | 중간 | 자가수정 2회, 폴백 봇, 실패 사례 로그 공개 |
| 4 | LLM 비용 / 무료 티어 한도 | 낮음 | 컴파일 시점만 호출, 캐싱, 제공자 분산 |
| 5 | 특정 전략이 지배 → 리그 무의미 | 중간 | 4주차 밸런싱, 맵 다양화, 시즌 분리 |
| 6 | 프롬프트 주입 | 낮음 | 스키마 검증이 구조적 방어 |
| 7 | 4명 코드 스타일 편차 | 중간 | 1주차 컨벤션 확정, 사람 리뷰 필수 |
| 8 | 발표장 네트워크 장애 | 중간 | 사전 컴파일된 봇 5~6개를 DB에 준비 (대전·리플레이·리더보드는 LLM 불필요) + 녹화 영상 |

## 13. 데모 시나리오 (5분)

1. **[30초] 문제 제기** — "프롬프트를 잘 쓴다는 게 뭘까요? 측정할 수 있을까요?"
2. **[1분] 즉석 참전** — 심사위원에게 한 줄 받아 컴파일. 규칙 카드가 생성되는 화면을 그대로 보여줌
3. **[1분] 대전** — 기본 봇과 즉시 대전. 리플레이에서 규칙 발동 하이라이트로 "이 문장이 이 행동을 낳았다"를 연결
4. **[1분] 개선** — 프롬프트에 한 문장 추가 → 재컴파일 → 재대전 → **승률 변화 확인**
5. **[1분] 규모** — 100판 자동 대전 통계, 리더보드 반영
6. **[30초] 아키텍처** — "LLM은 등록 시점에만 개입합니다. 대전은 LLM 없이 돌아갑니다."

## 14. 성공 기준

**필수 (이게 안 되면 실패)**

- 프롬프트 → 컴파일 → 대전 → 리플레이 전 과정이 끊김 없이 동작
- 정교한 프롬프트가 대충 쓴 프롬프트를 유의미하게 이김
- 처음 보는 사람이 설명 없이 1분 안에 봇을 등록

**목표**

- 규칙 발동 하이라이트 완성
- 리그 100판 자동 대전 및 Elo 반영
- 컴파일 성공률 90% 이상

**여유 있을 때**

- 두 번째 게임 지원 (게임 엔진 인터페이스 분리의 증명)
- 봇 대전 관전 공유 링크
- 프롬프트 버전 A/B 비교

## 15. 범위 밖 (명시적으로 안 함)

- 실시간 LLM 추론 (매 턴 호출) — 아키텍처상 배제
- 3D 렌더링
- 모바일 최적화 (반응형까지만)
- 소셜 기능, 댓글, 팔로우
- 사용자 코드 실행 (샌드박스) — 프롬프트 방식으로 대체
