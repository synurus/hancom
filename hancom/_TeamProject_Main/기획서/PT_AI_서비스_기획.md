# PT/헬스 트레이너용 AI 회원관리 SaaS 기획

## 프로젝트 개요

- **아이템**: PT/헬스 트레이너용 AI 회원관리 SaaS
- **타겟**: 개인 PT샵, 소규모 헬스장 트레이너
- **결제모델**: 무료~프로까지 3단계 요금제(하단 "요금제" 참고), 자유 게시판(커뮤니티)은 게시물 홍보(광고) 수익으로 별도 창출
- **팀 규모/기간**: 4인, 6주
- **성격**: 팀플 평가용 + 실서비스(창업) 겸함

## 핵심 원칙

AI는 운동/식단 처방을 대신하지 않는다. 국가공인 자격증을 가진 트레이너가 직접 판단해야 하는 영역(운동 처방, 식단 처방)은 AI가 대체하거나 결정하지 않는다. AI는 트레이너의 반복 행정업무 자동화와 데이터 가공만 담당하고, 최종 판단은 항상 트레이너가 내린다.

이 원칙이 필요한 이유:
- **책임 소재**: 부상 이력, 관절 상태 등을 실시간으로 봐야 하는 판단을 AI가 텍스트만으로 내리면 부상 발생 시 책임 소재가 애매해짐
- **신뢰 구조**: 회원이 결제하는 이유는 "자격증 가진 사람이 직접 봐준다"는 것. AI가 그 자리를 대신하면 서비스 가치가 오히려 깎임

## 핵심 기능 (14개)

| # | 기능 | 내용 |
|---|---|---|
| 1 | 비전 이미지인식 (식단 기록) | 식사 사진 업로드 → 비전 AI가 음식 종류 판별 → 영양성분DB 매칭 → 칼로리/영양소 추정 → 트레이너에게 리포트 전달. 양 추정은 근사치이므로 "1차 추정치, 트레이너가 필요시 보정" 포지셔닝 유지. **일반 하루 권장 섭취량 대비 부족 영양소 비교**도 함께 제공하되, 개인 맞춤 처방이 아닌 일반 통계 비교 정보로 한정하고 트레이너 화면에만 우선 표시 → 트레이너가 확인 후 회원에게 코멘트 |
| 2 | 자유 게시판 | 가입한 모든 유저가 특정 주제 제한 없이 자유롭게 글을 올릴 수 있는 오픈 커뮤니티. 게시글 노출 순서는 **조회수·추천수 기준 정렬**(AI 미사용). 수익모델은 게시물 홍보(광고) 수익 |
| 3 | 트레이너-회원 1:1 대화 | 트레이너는 본인이 담당하는 회원하고만 1:1로 메시지 가능 (트레이너-회원 매칭 데이터 구조 선행 필요) |
| 4 | 바디체크 시각화 | 인바디/체성분 데이터, 정기 사진을 넣으면 AI가 변화 추이 그래프+요약 자동 생성. 최종 코멘트는 트레이너가 작성 |
| 5 | 회원정보 관리 | 기본 회원 CRUD, 프로필 관리 |
| 6 | 이탈 위험 알림 | 출결 패턴 분석해서 "이탈 위험" 트레이너에게 알림 (판단이 아니라 패턴 감지) |
| 7 | 신규 문의 챗봇 | 가격·시간·프로그램 소개 등 단순 문의는 AI가 1차 응대, 운동/식단 관련 질문은 트레이너 연결 |
| 8 | AI 모더레이션 | 커뮤니티 부적절 게시물(욕설, 스팸) AI 1차 자동 필터링. **요금제 무관 전 회원 상시 적용(보안 고려사항 절 원칙과 일치)**. (기존 "맞춤 피드 추천"은 폐기 결정 — 게시글 노출은 기능2의 조회수·추천수 정렬로 대체) |
| 9 | 회원 수면 관리 (삼성헬스 연동) | 회원이 삼성헬스 앱 데이터(수면 시간, 수면 단계 등)를 연동하면 자동으로 가져와서 트레이너 화면에 추이 표시. 삼성헬스 자체 API는 파트너 승인이 필요해 접근이 제한적이므로, 대안으로 안드로이드 Health Connect(여러 건강 앱 데이터를 모아주는 구글의 통합 API, 삼성헬스 데이터도 포함)를 통한 연동을 우선 검토. **Health Connect는 안드로이드 온디바이스 API라 네이티브(또는 Capacitor 등 래핑) 앱 없이는 접근 불가 — 6주 MVP는 웹 우선이므로 이번 빌드 범위에서 제외, 웹 완성 후 앱화 시점에 재검토** |
| 10 | 수업예약/스케줄 관리 | 회원이 트레이너의 빈 시간을 확인하고 수업을 예약, 트레이너는 전체 일정을 캘린더로 관리. 예약 확정/취소/변경 알림은 **카카오 알림톡**으로 자동 발송(국내 서비스 표준 채널, 카카오 비즈니스 채널 사전 등록 필요) |
| 11 | 부상 이력 기록 | 회원의 과거 부상·관절 상태 등을 트레이너가 직접 입력해 프로필에 기록·조회. **AI는 이 데이터를 요약·판단하지 않고 단순 기록·조회만 제공** — 운동 처방 시 참고 판단은 트레이너가 직접 함(핵심 원칙에서 짚은 "책임 소재" 문제와 직결되는 데이터라 AI 판단 개입 배제) |
| 12 | QR코드 체크인 | 매장 입구에 고정 QR코드를 부착해두고, 회원이 본인 스마트폰 카메라로 스캔하면 출결 기록. 매장 쪽 스캔 단말·하드웨어 불필요(QR 포스터만 있으면 됨), 브라우저 카메라 API + QR 디코딩 라이브러리로 처리. AI 미사용, 단순 기록 기능이며 6번(이탈 위험 알림)의 출결 데이터 입력 소스로 연결. **주의**: 고정 QR은 캡처·공유로 원격 체크인 악용 가능 — 필요시 QR 주기적 교체 또는 위치 확인 병행 검토. **구현 흐름**: QR에는 회원 정보 없이 매장 ID만 인코딩 → 스캔 시 로그인 세션에서 회원 ID 확인(QR 자체가 아니라 로그인 정보로 "누구인지" 판단) → 서버(Next.js API 라우트 또는 서버 액션)가 회원ID+매장ID+시각을 조합해 DB 출결 테이블에 기록. **요금제 무관 전 회원 공통 제공** — 이유: ① 무료 티어에 이미 "회원정보 관리(최대 5명)"가 포함돼 있는데 출결을 막으면 등록만 하고 관리는 못 하는 반쪽짜리 기능이 됨, ② 기능6(이탈 위험 알림, 라이트부터 유료)의 유일한 데이터 소스라 무료 단계부터 출결을 쌓아둬야 유료 전환 즉시 의미 있는 알림이 나옴(데이터 웜업). 무료 유저 출결 처리로 늘어나는 DB·Functions 호출 비용은 별도 시스템 구축 없이 기존 운영비용(Vercel 호스팅/DB) 안에서 흡수 |
| 13 | 운동 세션 기록 | "블록 추가" 클릭으로 운동 블록을 만들고, 블록 안에 **운동종목·중량·세트수·횟수**를 입력하는 방식. 세션 하나에 블록을 여러 개 쌓아 그날 수행한 전체 운동을 기록(예: 벤치프레스 블록 + 스쿼트 블록 + 데드리프트 블록). AI 미사용, 순수 입력 폼 + DB 저장이라 구현 난이도 낮음. 과거 블록 조회로 회원별 운동 이력·중량 변화 추적 가능 — 4번(바디체크 시각화)과 달리 "실제 그날 무엇을 했는지"의 원본 기록 |
| 14 | 회원별 목표 설정 & 진행률 트래킹 | 회원 목표(목표 체중·근육량 등)를 입력해두면, 4번(바디체크)에 쌓인 체성분 데이터로 목표 대비 진행률을 자동 계산·시각화(달성률 %, 남은 목표치). 새 AI 호출 없이 기존 데이터 재활용이라 추가 비용 없음 — 순수 계산/그래프 로직 |

## 요금제 (3단계)

**결정**: 팀/헬스장 요금제는 삭제 — 트레이너 5인 이상을 한 계정으로 묶어 쓰는 구조 자체가 바람직하지 않다고 판단, 모든 트레이너는 개인 단위로 무료/라이트/프로 중 선택해 가입. 이에 따라 "다중 트레이너 계정 관리"(헬스장 조직 단위 관리) 기능도 함께 폐기 — 예전에 지적했던 "팀 요금제엔 조직(헬스장) 엔티티가 스키마에 없다"는 위험요소는 이 결정으로 해소됨.

**참고**: 이 표는 실서비스 전체 로드맵 기준이며(기능9 포함), 6주 팀플 MVP 빌드 범위와는 별개임 — 빌드 범위 결정은 "남은 빌드업 단계" 절 참고. 또한 AI 모더레이션(필터링)과 QR코드 체크인(출결 기록)은 요금제와 무관하게 전 회원에게 항상 제공되는 공통 기능이라 아래 표의 유료 단계 목록에는 포함하지 않음.

| 단계 | 이름 | 가격 | 이용 가능 기능 |
|---|---|---|---|
| 1 | 무료 | 0원 | 자유 게시판 무제한 이용(AI 모더레이션 상시 적용), 회원정보 관리(최대 5명, 초과 불가), QR코드 체크인(출결 기록) |
| 2 | 라이트 | 월 9,900원 (트레이너 1인) | 1단계 전체 + 회원정보 관리 **기본 5명 포함**(초과 시 1인당 월 2,000원 추가) + 바디체크 시각화 + 이탈 위험 알림 + 수업예약/스케줄 관리 + 회원 수면 관리 + 부상 이력 기록 + 운동 세션 기록 + 회원별 목표 설정·진행률 트래킹 |
| 3 | 프로 | 월 29,900원 (트레이너 1인) | 2단계 전체 + 회원정보 관리 **기본 10명 포함**(초과 시 1인당 월 2,000원 추가) + 비전 이미지인식(식단 기록) + 트레이너-회원 1:1 대화 + 신규 문의 챗봇(기존 팀 전용에서 이관) |

### 관리 회원 초과 과금 (기존 "관리 회원 상한"에서 변경)

**결정 배경**: 트레이너 1인이 계정 하나만 결제하고 다른 트레이너의 회원까지 같은 계정으로 관리하는 계정 공유·전대 악용을 막으려 했던 게 출발점. 처음엔 하드 상한(예: 30명)을 검토했으나, **하드 상한은 상한 이하로만 나눠 담으면 여전히 공유를 못 막는다는 한계**가 있어(트레이너 2명이 15명씩 나눠 담아도 30명 이하) 기각. 대신 **기본 포함 인원 + 초과분 종량 과금(1인당 월 2,000원)** 방식으로 전환.

**이 방식이 계정 공유의 "비용 회피" 유인을 없애는 이유**: 트레이너 2명이 계정을 나눠 쓰든 각자 따로 결제하든, 총 관리 인원이 같으면 총 청구 금액이 거의 같아짐(예: 라이트 2계정으로 각 15명씩 = 2×(9,900+10명×2,000)=59,800원, 라이트+오버플로 1계정으로 30명 = 9,900+25명×2,000=59,900원 — 거의 동일). 계정을 합쳐도 아껴지는 비용이 없으므로 공유할 금전적 이유가 사라짐.

**주의 — 여전히 해결 못 하는 부분**: 이 과금 방식은 비용 회피 유인만 없앨 뿐, "실제로 그 회원을 담당하는 트레이너가 맞는지"를 확인하는 신원 검증은 아님. 데이터 접근 권한 자체를 통제하려면 동시 로그인 세션 제한이나 회원 등록 감사 로그 같은 별도 장치가 필요 — 이건 아직 미해결로 남겨둠.

**한계비용 검증**: 초과 1인당 2,000원이 실제 원가를 웃도는지 확인 — 라이트 추가 1인당 한계비용(알림톡+AI) ≈ 219원(2,000원 대비 여유 큼), 프로 추가 1인당 한계비용(비전인식 포함) ≈ 1,519원(2,000원 대비 약 481원 이익) — 두 단계 모두 초과 과금이 원가를 웃돌아 재무적으로 안전

**수지타산 반영 방식**: 이 문서 전체가 "트레이너 1인 평균 회원 10명"을 전형적 사용량으로 가정해왔음(알림톡·바디체크·비전인식 물량 산정에 반복 사용). 프로(기본 10명)는 이 전형적 사용량과 기본 인원이 정확히 일치해 초과 과금이 0원으로 모델링됨. **라이트만 기본이 5명이라, 전형적 사용량(10명)이 곧 5명 초과 상태 — 아래 "실제 순이익 추정"에서 라이트 매출을 9,900원이 아니라 9,900+5명×2,000원=19,900원으로 반영**

### 요금제 접근 제어 (Entitlement 검증)

**문제**: "보안 고려사항" 절의 인가 원칙("이 트레이너가 이 회원 담당자인지 서버가 재확인")은 매칭 여부만 다루고, "이 트레이너의 요금제가 이 기능을 쓸 수 있는지"는 검증하지 않음. 프론트엔드에서 메뉴만 숨기면 결제 검증과 동일한 방식(개발자도구·직접 API 호출)으로 우회 가능해 보안 기능이 아님.

**설계**
- Neon Postgres에 `trainer_subscriptions`(trainer_id, plan, updated_at) 테이블 구성 — 트레이너별 현재 요금제를 여기 한 곳에만 저장. `plan` 값은 **FREE/LIGHT/PRO 세 가지뿐**(팀/헬스장 요금제 삭제 결정으로 TEAM 값 없음)
- **판단 근거는 항상 이 테이블**: 클라이언트가 보내는 planId는 신뢰하지 않음(결제 금액 검증 원칙과 동일 — "판단 근거는 클라이언트가 아니라 서버가 갖는다")
- 토스페이먼츠 결제 승인 콜백에서만 `trainer_subscriptions.plan` 값을 갱신 — 결제 성공 확인 없이 클라이언트 요청만으로 plan을 바꿀 수 없게 함
- 기능별 최소 요금제를 코드 상 하나의 매트릭스로 정의(예: `{ 챗봇: 'PRO', 비전이미지인식: 'PRO', 채팅: 'PRO', ... }`)하고, 각 API 라우트/서버 액션 진입부에서 공통 함수(`requirePlan(trainerId, '기능명')`)로 매 요청마다 검증 — 트레이너-회원 인가 검증과 동일한 위치(서버 진입점)에서 처리. **AI 모더레이션(필터링)·QR코드 체크인(출결)은 이 매트릭스에서 제외** — 요금제 무관 상시 허용 기능이라 별도 게이트 없이 통과
- **수량 검증 — 무료/유료가 서로 다르게 동작**: 무료 요금제 "회원 최대 5명"은 회원 추가 API가 매 요청마다 현재 회원 수를 서버에서 다시 세어 초과 시 등록 자체를 차단(클라이언트가 보낸 카운트 신뢰 안 함). 라이트 이상은 차단하지 않고 대신 **초과 과금 방식**("관리 회원 초과 과금" 절 참고) — 서버가 매 결제 주기마다 `현재 회원 수 − 기본 포함 인원`을 계산해 초과분×2,000원을 다음 청구에 자동 합산(토스페이먼츠 정기결제·빌링키 사용), 등록 시점엔 "다음 달 예상 추가 청구액"을 트레이너 화면에 안내
- **다운그레이드 시 데이터 보존**: 요금제를 낮춰서 특정 기능 접근이 막혀도 기존 데이터(채팅 내역, 식단 기록 등)는 삭제하지 않고 보존 — 재구독 시 그대로 복구되도록

### 커뮤니티 모더레이션(AI 필터링) 비용 추정

**전제**: 기능8의 필터링은 요금제 무관 게시판 전체에 상시 적용되므로, 트레이너별 유료 사용량이 아니라 **전체 가입자(무료 포함) 게시물 수** 기준으로 계산. 단가는 앞 절 표와 동일하게 Haiku급 약 3원/건.

**월 발송량 추정** — 초기 가입자 시나리오(무료 50 / 라이트 20 / 프로 18, 합계 88명 — 팀/헬스장 삭제로 기존 팀 소속 트레이너 10인은 개인 프로 가입으로 환산) 기준, 1인당 월 평균 게시글+댓글 3건 가정 → 88명 × 3건 ≈ 264건/월

무료 가입자가 만드는 이 비용은 유료 트레이너에게 공평하게 배분할 근거가 약해(무료 유저 행동 때문에 발생하는 비용이라) 아래 순이익 계산에서는 전체 매출에서 차감하는 공용 비용으로만 반영하고, 개별 요금제 순이익 표에는 나누지 않음.

## 과금 책임 소재

- **과금 계정 주체**: Vercel AI Gateway 사용량은 팀/서비스 명의 계정으로 일원화해서 청구·관리한다. 팀원 개인 API 키를 프로덕션이나 공용 개발 환경에 사용하지 않는다.
- **예산 상한 설정**: 위 표에서 확인했듯 비전 이미지인식 기능의 원가율이 높으므로, Vercel AI Gateway의 budget cap·사용량 알림(alert)을 반드시 설정해서 예상치를 초과하는 과금이 발생하면 사전에 통보받도록 한다. 설정 전에는 실서비스로 전환하지 않는다.
- **이상치 사용자로 인한 초과분**: 식단 사진을 비정상적으로 많이 업로드하는 등 이상치 사용자로 인한 초과 과금은 서비스 운영 주체가 우선 부담하되, 반복적 어뷰징이 확인되면 fair-use 정책에 따라 해당 계정을 제한한다. 이 근거를 이용약관에 명시해 둔다.
- **팀플 평가 기간 vs 실서비스 기간**: 6주 팀플 평가 기간의 테스트성 API 호출 비용과, 이후 실서비스 전환 시의 실사용 비용을 분리해서 관리한다. 평가 기간 비용은 팀 공동 부담, 실서비스 전환 이후 비용은 서비스 운영 주체(창업 시 회사)가 부담하는 것으로 사전에 합의해 둔다.

## AI 모델 선정

- **Vercel AI Gateway + Claude 계열 모델** 사용. Next.js·Vercel 배포 전제라 AI SDK로 provider/model 문자열만 지정해서 여러 모델을 하나의 게이트웨이로 관리(모델 교체·장애 대응·비용 추적 용이)
- 식단 사진 인식(비전 이미지인식)은 이미지 이해가 가능한 멀티모달 모델이 필요함
- **작업 난이도별 모델 등급 분리**로 비용 최적화:
  - 단순 작업(이탈 위험 알림 패턴 분석, 신규 문의 챗봇 응대, 커뮤니티 모더레이션 등) → 저렴하고 빠른 모델(예: Haiku급)
  - 복잡한 작업(식단 사진 인식·영양소 추정, 바디체크 추이 요약) → 더 강력한 멀티모달 모델(예: Sonnet급)

## 보안 고려사항

- **인증**: Clerk 사용 (Vercel 마켓플레이스 네이티브 통합 — 환경변수 자동 프로비저닝, 통합 결제, 로그인 UI 컴포넌트 제공). 구글·깃허브 등은 기본 지원, 카카오는 커스텀 OAuth로 추가. 카카오 연동 시 **비즈니스 앱 전환 여부**를 먼저 체크할 것(과거 이 부분을 몰라서 권한 문제 겪은 적 있음)
- **회원가입 방식**: 이메일+비밀번호 자체 가입은 넣지 않고 **소셜로그인 전용(구글+카카오 등 2개 이상)**으로 구성. 비밀번호 저장·해싱·재설정 로직 자체가 없어져 공격 표면이 줄고, 특정 제공자 장애에 대비해 2개 이상 소셜로그인을 병행
- **인가 (★핵심 보안 사항)**: 트레이너-회원 매칭 기반, **모든 API 요청마다 서버단에서 권한 검증 필수**. 화면에서 버튼/메뉴만 숨기는 프론트엔드 처리는 우회 가능(개발자도구·직접 API 호출로 다른 트레이너의 회원 데이터에 접근 가능)하므로 보안 기능이 아님 — 실제 데이터를 응답하는 서버(API)가 매 요청마다 "이 트레이너가 이 회원의 진짜 담당자인지" DB로 재확인한 뒤에만 데이터를 반환하도록 구현. (DB에 쓰거나 로그인 확인이 필요한 모든 기능 — 회원가입, 부상이력 기록, QR체크인, 예약 등 — 이 원칙 동일 적용. Next.js에서는 API 라우트 또는 서버 액션으로 구현하며, Vercel 배포 시 서버리스 함수로 자동 처리되어 별도 서버 인프라 구축은 불필요)
- **민감정보**: 건강정보는 개인정보보호법상 별도 동의 필요한 민감정보. 필요 최소한만 수집
- **데이터베이스 구조**: 관계형 DB(Neon Postgres, Vercel 마켓플레이스 통합) 사용 — 회원-트레이너 매칭, 예약, 부상이력처럼 서로 연결된 데이터가 많아 관계형 구조가 적합
  - 일반 회원정보와 부상이력·건강정보는 **테이블 분리** — 부상이력 테이블은 접근권한을 더 좁게 설정
  - 누가 언제 부상이력을 조회했는지 **조회 로그** 기록 — 문제 발생 시 추적 가능하도록
  - 식단 사진 등 이미지는 DB에 직접 저장하지 않고 **Vercel Blob**에 저장 후 URL만 DB 컬럼에 저장
  - 회원 탈퇴 시 부상이력 등 민감정보 **파기 정책**을 개인정보처리방침에 명시
- **커뮤니티 모더레이션**: 욕설·스팸·불법 게시물(음란물, 도박·불법 광고 등)을 AI가 1차 자동 필터링해서 걸러내고, 애매한 건 신고 접수 후 최종 판단은 운영자가 수행
- **결제정보**: 카드번호 등은 우리 서버가 저장하지 않고 PG사(토스페이먼츠 등)가 처리 (PCI-DSS는 PG사 책임)
- **인프라**: HTTPS 기본 적용, API 키/시크릿은 환경변수 관리, 로그인 rate limiting
- **법적 문서**: 개인정보처리방침, 이용약관 (실서비스 지향이면 필수)

## 핵심 기능 구현 방법 (기능 1·2·3·4·5·6·7·8)

### 기능 1. 비전 이미지인식(식단 기록)

**검토한 방향**
1. 비전 LLM 단독 방식 — 사진 넣고 프롬프트로 음식명+칼로리 한 번에 요청. 구현 빠르나 양(그램수) 추정이 눈대중이라 오차 큼
2. 전용 인식 API + 영양 DB 방식(LogMeal, Nutritionix 등) — 정확도 높으나 API 비용·통합 작업 추가
3. **하이브리드(채택)** — 비전 LLM(Claude, Vercel AI Gateway·Sonnet급, "AI 모델 선정" 절과 동일 스택)으로 음식명만 판별 → USDA FoodData Central 같은 무료 영양 DB에서 칼로리/영양소 조회. 별도 유료 인식 API 없이 기존 스택 안에서 처리 가능

### 기능 2. 자유 게시판

**검토한 방향**
1. 별도 CMS/포럼 솔루션(Discourse 등) 연동 — 기능은 풍부하나 별도 인프라·인증 재연동 필요해 스택과 호환 문제 생김(Clerk 인증과 별개 계정 체계가 생길 수 있음)
2. **Neon Postgres 자체 테이블 + Next.js 서버 액션(채택)** — `posts`/`comments` 테이블을 기존 Neon Postgres에 추가하고 Next.js 서버 액션/API 라우트로 CRUD. 인증은 이미 도입한 Clerk 그대로 사용, 이미지 첨부는 Vercel Blob(식단 사진과 동일 저장소) 재사용 — 새 벤더 추가 없이 기존 스택 안에서 호환

**검색/정렬**: 초기 규모(가입자 수백 명 수준)는 Postgres `ILIKE` 검색으로 충분, 별도 검색엔진(Elasticsearch 등) 불필요 — 트래픽 커지면 Postgres full-text search 확장으로 단계적 전환 가능해 호환성 유지

**노출 순서(정렬)**: 기존에 검토했던 AI 맞춤 피드 추천은 폐기 결정 — 대신 `posts.view_count`/`posts.like_count` 컬럼 기준 `ORDER BY` 정렬로 구현. AI 호출 없이 순수 DB 쿼리라 추가 비용·구현 공수 없음

### 기능 3. 트레이너-회원 1:1 대화

**전제**: 매칭 데이터 구조(트레이너-회원 매칭 테이블) 선행 필요

**매칭 성사 방식(결정)**: 트레이너가 먼저 (아직 매칭 안 된) 회원을 선택 → 시스템이 1회성 초대 링크 생성 → 트레이너가 그 링크를 회원에게 전달 → 회원이 링크로 들어와 수락하면 매칭 확정. 구현:
- `invites`(id, trainer_id, token, status, expires_at) 테이블 — 트레이너가 회원 등록 화면에서 "초대 링크 생성" 클릭 시 토큰 발급(만료시간 설정, 1회용). **토큰은 충분한 엔트로피의 랜덤 값**(순번·짧은 코드 금지) — 초대 수락 엔드포인트는 로그인 전 접근이라 토큰 자체가 유일한 권한 증명이기 때문
- 회원이 링크 클릭 → Clerk 로그인(신규면 가입, 기존이면 로그인) → 서버가 토큰 유효성(만료·사용 여부) 확인 → 통과하면 `matches`(trainer_id, member_id) 레코드 생성 + `invites.status`를 사용 완료로 변경
- **이 흐름이 Clerk 가입 시 트레이너/회원 역할 구분도 함께 해결**: 초대 링크를 거쳐 가입한 사람은 회원 역할로 확정, 트레이너는 별도 가입 진입점(예: `/trainer/signup`)으로 구분 — 이 트레이너용 가입 진입점 자체의 세부 설계는 아직 미정(우선순위 낮은 별도 결정 사항)
- **무료 "5명 제한" 체크 시점**: 회원 수락 시점이 아니라 **초대 링크 생성 시점**에 상한 검증(미사용 초대 + 확정된 매칭 합산 카운트) — 수락 시점에 막으면 회원이 가입까지 마쳤는데 거절당하는 나쁜 경험이 생기기 때문

**검토한 방향**
1. **Vercel Functions WebSocket(채택)** — Fluid Compute 기본 지원으로 별도 벤더 없이 Vercel+Neon Postgres 스택 안에서 구현 가능. `matches`(trainer_id, member_id) + `messages`(match_id, sender_id, content, read_at) 테이블을 Neon Postgres에 구성하고, API 라우트가 매 요청마다 "이 트레이너가 이 회원의 진짜 담당자인지" 재검증(보안 고려사항 절의 인가 원칙과 동일 적용)
2. Pusher/Ably 등 관리형 Pub/Sub — 구현은 빠르나 별도 비용·벤더 추가되어 제외

**읽음 표시**: `messages.read_at` 컬럼 + 상대가 채팅방 열 때 업데이트. 구현 난이도 낮음
**푸시 알림**: 앱이 켜져 WebSocket 연결 중일 때는 추가 작업 거의 없음. 앱이 꺼지거나 백그라운드일 때 OS 알림은 웹 푸시(서비스 워커+VAPID 키) 별도 구현 필요 — MVP(6주) 범위에서는 읽음 표시까지만 넣고 푸시는 이후 단계로 미루는 것도 방법

### 기능 4. 바디체크 시각화 — 3D 구현 여부

**검토한 방향**
1. 3D(Three.js/React Three Fiber + 사람 메시 + 모프 타겟) — 회전·조작 가능한 인터랙티브 뷰, 3D 에셋 제작+모프 타겟 세팅 공수가 커서 4인 6주 팀플 일정엔 부담
2. **2D 실루엣 + 색상 히트맵(인바디 리포트 방식, 채택)** — 부위별 색상으로 체성분 변화 표시, 구현 훨씬 빠름. "변화 추이 그래프+요약" 요구사항은 이 방식으로 충분히 충족

**추천**: 6주 일정 고려해 2번으로 MVP 구성, 실서비스 전환 후 차별화 포인트로 필요해지면 1번(3D) 추가 검토

### 기능 5. 회원정보 관리

**검토한 방향**
1. 별도 CRM 솔루션 연동 — 기능 풍부하나 별도 계정 체계·API 연동 필요해 인가 원칙(보안 고려사항 절)을 그쪽 시스템에도 이중으로 적용해야 함
2. **Neon Postgres `members` 테이블 + Clerk `userId` 연결(채택)** — 회원 프로필은 Neon Postgres 자체 테이블로 CRUD, Clerk가 발급하는 `userId`를 외래키로 연결해 트레이너-회원 매칭(기능 3)·부상이력(기능 11) 등 다른 테이블과 동일한 식별자 체계 공유. 모든 조회/수정 요청은 서버에서 로그인 세션 기준으로 재검증(보안 고려사항 절 원칙과 동일 적용) — 별도 인증 체계 없이 완전히 호환

### 기능 6. 이탈 위험 알림

**검토한 방향**
1. AI(LLM)가 출결 데이터 전체를 보고 이탈 여부까지 직접 판단 — "핵심 원칙"(AI는 판단하지 않고 트레이너가 최종 판단)과 충돌해 제외
2. **규칙 기반 1차 필터 + LLM 요약 하이브리드(채택)** — Vercel Cron이 주기적으로 회원별 출결(QR체크인 기능 12 데이터) 집계 → 미리 정한 임계값(예: 2주 연속 미출석)으로 "이탈 위험 후보"를 규칙으로 걸러냄(여기가 실제 판단 기준, AI 아님) → 후보만 Haiku급 LLM(Vercel AI Gateway, 기존 스택)이 "최근 2주간 3회 예약 후 2회 노쇼" 같은 설명 문장을 생성해 **트레이너 앱 화면(인앱)에 표시**. AI는 설명문 생성만 담당하고 실제 판단은 규칙이 하므로 "핵심 원칙"과 정확히 일치
   - **알림 채널 주의**: 카카오 알림톡은 사전 승인된 템플릿의 변수 슬롯만 채울 수 있어 LLM이 생성한 자유 문장을 그대로 보낼 수 없음. 알림톡 발송은 "[이탈위험] {회원명} 회원님 최근 {기간} {결석횟수}회 결석 — 확인 부탁드립니다" 같은 고정 템플릿에 숫자만 채워 보내고, LLM이 만든 상세 설명 문장은 인앱 화면에서만 노출(비용·발송량 추정은 "카카오 알림톡 발송 비용 추정" 절 참고)

### 기능 7. 신규 문의 챗봇

**검토한 방향**
1. 별도 챗봇 플랫폼(Dialogflow, Chatfuel 등) 연동 — 기능은 빠르게 붙지만 별도 서비스·API 키 관리 늘어나 기존 Vercel AI Gateway 스택과 이원화됨
2. **고정 FAQ + Haiku급 LLM(Vercel AI Gateway, 채택)** — 가격·시간·프로그램 소개 등은 고정 FAQ 텍스트를 프롬프트에 컨텍스트로 넣어 LLM이 응답. 질문이 운동/식단 처방 영역으로 판단되면(키워드 매칭 또는 LLM 분류) 즉시 "트레이너 연결" 안내로 전환 — "핵심 원칙"(AI가 운동/식단 처방 대체 금지)과 일치. 기존 AI Gateway·모델 등급 분리 체계를 그대로 재사용해 새 벤더 없이 호환

### 기능 8. AI 모더레이션 — 필터링 구현

**검토한 방향**
1. 금칙어 필터 — 업로드 시점 즉시 차단, 구현 쉽고 무료. 단점: 초성·특수문자 우회에 취약, 맥락 파악 불가
2. 전용 모더레이션 API(OpenAI Moderation, Google Perspective 등) — 카테고리별(욕설/성적/폭력) 점수 제공, 빠르고 대부분 무료. 단점: 별도 벤더, 한국어 정확도 별도 검증 필요해 제외
3. **금칙어 필터(1차) + LLM 판단(2차) 하이브리드(채택)** — 게시 즉시 금칙어 필터로 명백한 건 먼저 차단, 통과한 글은 비동기로 Haiku급 LLM(Vercel AI Gateway, "AI 모델 선정" 절과 동일 스택)이 2차 검사. 애매한 건 신고 접수 후 운영자 최종 판단("보안 고려사항" 절의 커뮤니티 모더레이션 원칙과 동일)

**적용 범위**: 게시자의 요금제와 무관하게 게시판(기능2)의 모든 글에 상시 적용 — 무료 티어 회원 글도 예외 없음(같은 공용 게시판을 유료 회원도 함께 보므로). 비용도 "트레이너 1인당 사용량"이 아니라 **전체 가입자(무료 포함) 게시물 수** 기준으로 계산해야 함 — "카카오 알림톡 발송 비용 추정"과 같은 성격의 서비스 전체 공용 비용이라 아래 수지타산 절에 별도 반영

## 구현 순서 (Build Order)

실제 코드 작성 전 단계 — 무엇을 어떤 순서로 만들지만 정리. 뒤 단계가 앞 단계의 데이터 구조·인프라를 그대로 재사용하는 의존관계 기준 순서라, 순서를 바꾸면 재작업이 생김. 기능9(수면관리)는 앞서 결정한 대로 제외.

### Phase 0 — 기반 인프라
- **포함**: 프로젝트 스캐폴드(Next.js App Router, Vercel 배포) / Clerk 인증(구글·카카오 소셜로그인, **트레이너·회원 두 역할 모두** — QR체크인·채팅·예약이 전부 회원 쪽 로그인 세션을 전제로 하므로 Phase 0에서 같이 설정) / Neon Postgres 연결 / 기본 스키마(`trainers`, `members`, `trainer_subscriptions`, `invites`)
- **이유**: 이후 모든 기능이 "누가 로그인했는지"와 "DB 연결"을 전제로 함 — 여기가 흔들리면 전부 다시 손대야 함
- **완료 기준**: 트레이너·회원 두 역할 모두 로그인 성공 후 Neon Postgres에 레코드 생성 확인, Vercel 배포된 실제 URL에서 로그인 동작

### Phase 1 — 회원 관리 뼈대 (기능5, 기능3의 매칭 테이블·초대 흐름)
- **포함**: 회원 CRUD / 트레이너-회원 매칭 — **트레이너가 회원 선택 → 초대 링크 생성 → 회원이 링크로 수락하면 `matches` 확정**("핵심 기능 구현 방법" 기능3 절의 "매칭 성사 방식" 참고) / 요금제 접근 제어(`requirePlan`) 최초 적용 — 무료 "5명 제한"부터. **`trainer_subscriptions.plan`은 Phase 7(결제 연동) 전까지 실제 결제 콜백이 없으므로, 개발 단계에서는 시드 데이터/관리자 도구로 수동 설정해서 LIGHT·PRO 경로를 테스트**
- **완료 기준**: 트레이너가 초대 링크 생성 → 회원이 수락 → 매칭 확정까지 전체 흐름 동작, 무료 요금제에서 6번째 초대 링크 생성 시도 시 서버가 차단(수락 시점이 아니라 생성 시점), 수동으로 plan을 LIGHT/PRO로 바꿔 상한이 달라지는지 확인

### Phase 2 — 출결 (기능12 QR코드 체크인)
- **포함**: QR 생성/스캔, 출결 테이블
- **이유**: 기능6(이탈 위험 알림)의 유일한 데이터 소스라 가능한 한 일찍 쌓아야 함(데이터 웜업 — "핵심 기능 구현 방법" 기능12 절 참고)
- **완료 기준**: 회원이 QR 스캔 시 출결 기록 저장, 무료 유저도 정상 동작 확인

### Phase 3 — 커뮤니티 (기능2 게시판, 기능8 모더레이션 필터링)
- **포함**: 게시글/댓글 CRUD / 조회수·추천수 정렬 / 금칙어 필터(1차) + Haiku LLM(2차) 검사
- **완료 기준**: 게시글 작성 시 금칙어 자동 차단 확인, 정상 글은 정렬 반영돼 노출

### Phase 4 — 운동/건강 기록 (기능13, 기능11)
- **포함**: 운동 세션(블록) 기록 / 부상 이력 기록(테이블 분리 + 조회 로그)
- **완료 기준**: 블록 추가로 운동 기록 저장·조회 가능, 부상이력 조회 시 조회 로그 남는지 확인

### Phase 5 — AI 기능 (기능1, 기능4, 기능6, 기능7)
- **포함**: Vercel AI Gateway 연동 / 식단 사진 인식 + 영양 DB 조회(기능1) / 바디체크 2D 히트맵(기능4) / 이탈위험 알림 — 규칙 기반 후보 판정 + LLM 요약문 생성까지(기능6, **알림톡 발송 자체는 Phase 6**) / 신규 문의 챗봇(기능7)
- **완료 기준**: 각 기능 API 호출 성공, budget cap 설정 완료 후 실제 호출 비용 로그로 확인, 기능6은 **Vercel Cron이 실제로 주기 실행되는지**(스케줄 로그) 별도 확인

### Phase 6 — 실시간/알림 (기능3 채팅, 기능10 예약, 기능6 알림 발송)
- **포함**: WebSocket 1:1 채팅 / 예약·스케줄 관리 / 카카오 알림톡(템플릿 사전승인 필요) — 예약 알림과 **Phase 5에서 만든 기능6 요약문의 슬롯 발송**을 여기서 함께 연결
- **주의**: 알림톡 비즈니스 채널 등록·템플릿 심사는 기간이 걸리므로 **Phase 6 착수 훨씬 전에 미리 신청 시작** 필요
- **완료 기준**: 매칭된 트레이너-회원 간 실시간 메시지 송수신 확인, 예약 확정 및 이탈위험 후보 발생 시 각각 알림톡 수신 확인

### Phase 7 — 목표 트래킹(기능14) + 결제 연동
- **포함**: 목표 설정/진행률(기존 데이터 재활용) / 토스페이먼츠 구독 결제 + 초과 과금 정산
- **완료 기준**: 목표 대비 진행률 표시 확인, 결제 승인 후 요금제(`trainer_subscriptions`) 갱신 확인

**미해결 — 확인 필요**:
- Phase 0~7 전체는 8단계인데 4인·6주 규모에 비해 분량이 많음. 6주 안에 전부 끝내기 어려우면 어디까지를 MVP로 자르고 어디부터 이후 단계로 미룰지 결정 필요(우선순위 후보: Phase 5~7은 AI·실시간·결제라 상대적으로 늦게 잘라도 되는 영역)
- **결정: Phase 7 실제 결제 연동까지 6주 목표에 포함** — Phase 1~6은 plan을 수동 시드로 개발·테스트하다가, Phase 7에서 토스페이먼츠 실결제로 전환
