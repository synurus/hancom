# 시니어 디지털 동행 서비스 — 기술 검토 대화 정리

> 4인 팀 / 4주 / AI 기반 프론트엔드 웹개발자 양성과정 / Claude Code 활용

---

## 1. 프로젝트 개요

정부24, 고용24 같은 공공·구직 사이트 이용을 어려워하는 어르신을 위한 **디지털 동행 서비스**.

**핵심 흐름 4단계**

| 단계 | 내용 |
|---|---|
| ① 니즈 파악 | AI 대화로 무엇이 필요한지 파악 ("일자리 구하고 싶어", "등본이 필요해") |
| ② 서비스 연결 | 목적에 맞는 사이트/앱을 골라 목적 페이지까지 연결 |
| ③ 실전 가이드 | 실제 화면에 마커·하이라이트로 사용법 안내 |
| ④ 결과물 생성 | 대화 내용으로 이력서·신청서를 AI가 작성, PDF 제공 |

**차별점** — 기존 서비스는 목록만 보여주거나 연습만 시키고 끝나지만, 이 서비스는 니즈 파악부터 실제 제출 준비까지 한 흐름으로 이어짐.

## 3. 기술 방식 검토

| 방식 | 마커 정확도 | 실시간성 | 평가 |
|---|---|---|---|
| **iframe** | 거의 불가 | O | 대부분 사이트가 `X-Frame-Options`로 임베딩 차단 + 동일 출처 정책으로 내부 DOM 접근 불가 |
| **서버 프록시** | 높음 | O | 구현 부담 큼, 사이트 복잡할수록 깨지기 쉬움 |
| **스크린샷 + 오버레이** | 높음(정적) | X | 어떤 사이트든 동작하나 스크롤 시 재캡처 필요 |
| **브라우저 확장** | 가장 높음 | O | 정확도 최고, 배포·설치 방식이 달라짐 |
| **CDP Screencast** | 높음 | O | 실시간 요구를 만족하는 방식 |

### CDP Screencast 요약

- **CDP** = Chrome DevTools Protocol. 브라우저를 외부에서 원격 제어하는 프로토콜
- **Screencast** = 브라우저가 렌더링 중인 화면을 이미지 프레임으로 실시간 전송하는 기능
- 흐름: 서버 헤드리스 크롬이 렌더링 → WebSocket으로 프레임 전송 → 클라이언트 canvas에 그림 → 사용자 클릭 좌표를 서버로 보내 `page.mouse.click()`으로 원격 조작
- 제약: 크로미움 계열만 지원 → **단, 이건 서버 쪽 렌더링 브라우저에만 해당.** 사용자는 이미지 스트림만 보므로 어떤 브라우저든 무관
- 트레이드오프: 사용자마다 브라우저 인스턴스가 필요해 리소스 소모 큼 (포트폴리오 규모에선 사실상 무관)

## 4. 예상 한계점 (서버 리소스 제외)

1. **보안/개인정보** — 로그인 시 주민번호·인증서가 중계 서버를 경유 → 개인정보보호법 이슈
2. **법적/약관** — 공공사이트 대부분 자동화(봇) 접근 금지 조항. 캡차 뜨면 자동화 차단
3. **마커 정확도** — 좌표 기반이라 사이트 UI 변경 시 가이드 깨짐, 유지보수 부담
4. **스트리밍 지연** — 타겟층이 지연에 더 민감할 수 있음
5. **AI 문서 신뢰성** — 이력서·신청서 할루시네이션 → 실제 제출 서류 오류·반려 위험
6. **접근성/UX** — 마커만으론 부족, 글씨 크기·음성 안내·터치 오차 고려 필요

> **핵심 벽 3가지:** 법적(자동화·개인정보) + 신뢰성(AI 문서 오류) + 유지보수(UI 변경 대응)

## 5. 법적 문제 해결 — 재설계 원칙

문제의 원인은 **"서버가 사용자 대신 실사이트를 조작한다"** 딱 하나.
캡차·봇탐지 우회는 리스크만 키우므로 제외하고, **행위 주체를 서버에서 사용자로 되돌리는 방향**으로 재설계.

| 안 | 내용 | 법적 안전도 | 구현비용 | 어필력 |
|---|---|---|---|---|
| **① 샌드박스 클론** | 실사이트 안 건드리고 흐름만 재현한 연습화면 제작 | ★★★ | 중 | 중 |
| **② 오픈API + 딥링크** | 공공데이터포털·워크넷 API로 실제 데이터 검색, 최종 지원은 딥링크 | ★★★ | 낮음 | 중 |
| **③ 화면공유 동행모드** | `getDisplayMedia()`로 사용자 화면을 공유받아 관찰만, 마커로 안내 | ★★★ | 높음 | **높음** |

**샌드박스 제작 수칙** — 로고·정부 상징 사용 금지, 명칭 변경, 픽셀 카피 X, 상단 고정 배너
`⚠️ 학습용 연습 화면입니다. 실제 신청은 접수되지 않습니다.`

## 6. 최종 채택 방향 — 화면공유 + 질문 시점 캡처 마커

### 수정 사항 2가지

1. **"사이트 내부 새창"이 iframe이면 실패** → 반드시 `window.open()`으로 **별도 탭/창**. 품는 게 아니라 옆에 띄우는 구조
2. **헤드리스 스크린샷의 서버 렌더링은 배제** → 서버가 다시 접속하면 법적 문제 부활. 가져올 건 "이미지에 좌표로 마커 얹는 기법"만, 이미지 출처는 반드시 화면공유

### 아키텍처

```
① window.open()으로 정부24 별도 창 (좌우 반반 배치)
② 최초 1회 getDisplayMedia() 허용 → 스트림 계속 유지
③ 질문 시점에 drawImage로 프레임 1장 캡처
④ 현재 화면 판별
⑤ 우리 창 canvas에 스샷 + 마커 오버레이
⑥ 어르신은 실제 창에서 직접 클릭 (자동화 아님 ✅)
```

화면공유는 **최초 1회만 허용**받으면 이후 몇 번이든 캡처 가능. `drawImage`는 백그라운드 탭에서도 동작.

### 난관 3가지와 대응

| 문제 | 대응 |
|---|---|
| **A. 마커 위치 판단** | 좌표 예측을 AI에 맡기지 말 것. 화면 판별=Claude 비전(분류), **버튼 위치=OCR(tesseract.js) 텍스트 탐색** ⭐, 안내 문구=사전 시나리오 JSON. OCR 실패 폴백(문장 안내+음성) 필수 |
| **B. 스샷 마커를 실제 창에서 다시 찾아야 함** (최대 UX 약점) | **Document Picture-in-Picture** — 항상 최상위 창이라 창 전환이 사라짐. Chrome/Edge 지원, 미지원 시 나란히 배치 폴백. 쓰는 팀 거의 없어 차별화 확실 |
| **C. 개인정보** | OCR은 클라이언트에서만(서버 전송 0건), Claude 비전은 화면 판별 시에만 다운스케일+입력필드 마스킹 후, 캡처는 메모리에만, 공유 전 안내 모달 |

### 향후 계획용 대안

- **크롬 확장** — 문제 B 완전 해결되나 과정 산출물로 평가 애매 + 설치 장벽
- **2디바이스 모드** — 세션 동기화 필요해 4주엔 과함
- **음성 안내만** — 문제 A/B/C 전부 회피, 최후 안전망

## 7. 4주 실행 계획

### 스코프 확정

| 단계 | 원안 | 4주 실현안 |
|---|---|---|
| ① 니즈 파악 | AI 대화 | 그대로 (Claude API) |
| ② 서비스 연결 | 실사이트 연결 | 공공 오픈API 검색 + 딥링크 |
| ③ 실전 가이드 | 서버 원격 조작 | 샌드박스 투어 + (도전) 화면공유 캡처 마커 |
| ④ 결과물 생성 | 이력서 PDF | 그대로 (클라이언트 PDF 생성) |

**시나리오는 3개로 고정** — 일자리 찾기 / 주민등록등본 발급 / 이력서 작성
(3개 완성 > 8개 반쯤)

### 이원화 전략

| 축 | 내용 | 상태 |
|---|---|---|
| **메인 축** | 샌드박스 클론 + 투어 엔진 | **완성 보장 필수** (3개 시나리오) |
| **도전 축** | 화면공유 + 캡처 마커 + PiP | 1개 시나리오, 3주차 판단 |

**연결 트릭:** 1주차에 스텝 JSON 스키마를 두 축이 공유하도록 설계 → `anchor` 타입만 바꿔(`data-tour` ↔ `ocr-text`) 시나리오 재사용 → 도전축 추가비용 급감

### 기술 스택

```
React + Vite + TypeScript
Tailwind CSS (시니어 전용 디자인 토큰)
Zustand (상태관리)
react-joyride 또는 자체 오버레이 (투어 가이드)
jsPDF + html2canvas (PDF, 한글 폰트 서브셋 필수)
Web Speech API (음성 입력/출력)
tesseract.js (클라이언트 OCR)
Claude API (대화 + 문서 생성 + 화면 판별)
백엔드: 없거나 API 키 숨김용 Vercel Serverless Function 1개
```

### 역할 분담

| 담당 | 영역 |
|---|---|
| A (팀장) | 아키텍처 + AI 대화 (챗 UI, 의도 분류, 라우팅) |
| B | 가이드 엔진 (오버레이/마커 시스템, 투어 스텝 JSON 스키마) |
| C | 샌드박스 화면 (정부24/고용24 클론 UI 3세트) |
| D | 결과물 + 디자인시스템 (이력서 폼, PDF, 접근성 토큰) |

> B가 투어 스텝을 JSON으로 정의하고, C는 화면에 `data-tour="apply-btn"` 속성만 심으면 자동으로 마커가 찍히는 구조 → 병렬 작업 가능

### 주차별 일정

- **1주차** — 시나리오 3개 확정, 디자인 시스템(폰트 18px+, 터치 48px+, 고대비), 투어 JSON 스키마 합의, **`CLAUDE.md` 작성**
- **2주차** — 각자 담당 영역 병렬 구현, 데일리 15분 스탠드업, PR 상호 리뷰
- **3주차** — 전체 흐름 통합 (가장 위험). **수요일까지 통합 완료 시 도전축 착수, 아니면 포기.** 실제 어르신 1~2명 테스트
- **4주차** — 버그·로딩/에러 상태·반응형, 배포(Vercel), README, 발표. **라이브 데모 백업 영상 필수**

### Claude Code를 4명이 쓸 때

- **`CLAUDE.md`를 1주차에 팀 합의로 작성** (폴더 구조, 네이밍, 상태관리 규칙, 금지 패턴) — 없으면 3주차 통합이 지옥
- 컴포넌트 props 타입은 사람이 먼저 정하고 구현을 AI에 맡기기
- AI가 짠 코드를 각자 **설명할 수 있어야 함** (발표 Q&A 대비)

## 8. 발표 핵심 문구

> "실사이트 가이드를 위해 서버 헤드리스 브라우저 원격 조작을 먼저 검토했으나, 공공사이트 약관의 자동화 접근 금지와 민감정보 서버 경유 문제를 확인했습니다. 이에 **조작 주체는 사용자에게 두고, 우리는 화면만 관찰하는** 구조로 재설계했습니다. `getDisplayMedia`로 사용자가 직접 접속한 화면을 공유받아 질문 시점의 프레임을 캡처하고, 클라이언트 OCR로 앵커를 탐색해 마커를 오버레이합니다. 우리 서비스는 대상 사이트에 단 한 건의 요청도 보내지 않으며, 캡처 이미지는 브라우저 메모리를 벗어나지 않습니다."

**강조할 차별점 3개**

1. 원스톱 흐름 — 대화부터 제출용 PDF까지 끊기지 않음
2. 기술 선택의 근거 — 법적·보안 검토를 거친 재설계
3. 접근성 우선 설계 — 시니어 디자인 토큰, 음성 안내, 대형 터치 타겟
