## 0. 새 대화 시작할 때

**이 프로젝트는 두 종류의 "기억"을 같이 쓴다 — 상황에 따라 다른 걸 쓴다.**

### (A) 이 환경(Claude Cowork)의 프로젝트 메모리 — 같은 프로젝트에서 새 세션을 열 때

이 세션이 동작하는 환경은 대화가 끝나도 유지되는 **프로젝트 메모리**를 따로 갖고 있다
(`zeteo_partc.md`·`zeteo_sian.md`·`zeteo_spec_v3.md` 3개 파일). 같은 프로젝트에서 새
대화를 시작하면 이 파일들은 **자동으로 다시 읽힌다** — 파일을 다시 올릴 필요가 없다.
이 인수인계 문서보다 더 자주, 더 세밀하게 갱신되는 "1차 기록"이라고 보면 된다(예: 이번
botVote 이관·토큰 감사 내역은 이 문서보다 먼저 메모리에 기록됨). 다만 **다른 환경(다른
AI 도구, 다른 사람의 컴퓨터)에서는 안 보인다** — 그래서 이 인수인계 `.md` 파일이 여전히
필요하다: 팀원이 읽거나, 프로젝트 메모리가 없는 곳에서 새로 시작할 때의 "이식 가능한" 기록.

### (B) 이 문서 + 코드 — 사람이 읽거나 완전히 새로운 환경에서 시작할 때

아래를 같이 올리고 시작한다.

| 파일 | 역할 |
| --- | --- |
| `Zeteo_인수인계.md` | **이 문서** |
| `Zeteo 기술 구현 기획서 v3.0_files/saved_resource.html` | **최상위 기준 문서** (v2.0은 참고용, 8/10부로 v3.0이 최신) |

> Zeteo 프론트엔드 팀 프로젝트의 PART C(게임 화면)를 맡고 있어. 인수인계 문서 읽고 이어서 진행해줘.

### 절대 하지 않는 것

- 게임 로직 판단 (승패·과반·다음 페이즈) → A

### Git 규약

| 항목 | 규칙 |
| --- | --- |
| 브랜치 | `feat/game-ui` (로컬 `gameui`) |
| 병합 | `dev` 로 PR. **승인 1건 필수** |
| 매일 아침 | `git fetch origin --prune` → `git branch -avv` → 필요하면 `git merge dev` |
| 커밋 | `feat(ui): …` / `fix(ui): …` / `chore: …` |
| **`shared-types`** | 🔒 **잠김.** 파트 B를 거친다 |
| `main` | 김정현만 병합. 직접 push 금지 |
| **이 세션(Claude)** | `Scalmia/Zeteo`에 **push 권한 없음**(매번 확인됨). 항상 사용자 디스크에 파일만 반영 → 사용자가 직접 커밋·push |

### 커밋 전에 반드시

```powershell
git status
git diff --stat
```

**예상한 파일 수·줄 수와 다르면 커밋하지 말고 원인부터 찾는다.**

### 시험 병합 — 남의 브랜치를 미리 확인하는 법

```bash
git checkout -b trial origin/feat/game-ui
git merge --no-commit --no-ff origin/feat/server

git diff --cached --diff-filter=D --name-only   # ★ 조용히 삭제되는 파일
git diff --name-only --diff-filter=U            #   충돌로 뜨는 파일
npm run build -w frontend

git merge --abort
```

**`--diff-filter=D` 를 꼭 본다.** 삭제는 대부분 충돌로 안 뜬다.

### 병합 검증

```bash
git merge-base --is-ancestor origin/dev HEAD
echo $LASTEXITCODE   # 0 = 정말 병합됨, 그 외 = 아니다
```

`git show --stat HEAD`에 `Merge:` 줄이 없으면 병합 커밋이 아니다.

### 푸시된 커밋을 되돌려야 할 때

| 상황 | 방법 |
| --- | --- |
| 혼자 쓰는 브랜치, 아직 아무도 안 봄 | `git reset --hard <이전>` + `git push --force` |
| **PR이 열려 있거나 남이 볼 수 있음** | **새 커밋으로 되돌린다** |

### 자잘한 것

- `git fetch` 는 받아올 게 있을 때만 출력한다. **조용한 게 정상**
- `git rev-parse --short` 는 리비전을 **하나만** 받는다. 여러 개면 `git branch -avv`
- 줄바꿈(CRLF/LF) 문제 났었으면 `git restore .`(미커밋 작업 먼저 처리) — `git pull`은
  이미 디스크에 있는 파일을 다시 안 깐다
- 푸시가 갑자기 안 되면 DNS부터 의심 (`nslookup github.com 1.1.1.1`) — git 문제가 아닐 수
  있다

### CSS `display:contents` 조상 밑에서 절대 위치를 걸 땐 대상 요소를 신중히 고른다 (8/11, 신규)

모바일 미디어쿼리가 `.zt-main`·`.zt-chat`을 `display:contents`로 평탄화해 그 자식들을
`.zt-body`의 직계 flex 아이템으로 끌어올리는 트릭을 쓰고 있었다. 팝업을 "채팅 로그
영역에만" 가두려고 새 래퍼 div를 만들어 `position:relative`를 주려 했는데, 그 래퍼도
평탄화 대상에 포함시켜야 데스크톱·모바일 레이아웃이 안 깨진다 — 그러면 래퍼 자체가
`display:contents`가 되어 `position:relative`가 무효화되는 모순이 생긴다.
→ **해결은 래퍼를 안 만드는 것이었다.** 이미 평탄화 대상이 아닌(그리고 앞으로도 아닐)
`.zt-chat-log` 자체에 `position:relative`를 주고 그 안에 팝업을 직접 넣었다 — `overflow:
auto`인 컨테이너에 `position:absolute` 자식을 둬도 스크롤을 안 타는 CSS 특성(absolute
오프셋은 조상의 패딩 박스 기준, 그 박스는 스크롤로 안 움직임)을 이용한 것.
**기존 구조에서 이미 안정적인 요소를 찾아 거기 붙이는 게, 새 래퍼를 추가하는 것보다 나을
때가 있다.**

### `useEffect`로 prop 변화에 반응해 `setState`하면 린트가 걸린다 (8/11, 신규)

팝업을 ✕로 접었다가(peek) 새 페이즈로 넘어가면 자동으로 펴지게(`title` prop 변화 감지)
`useEffect(() => setPeeked(false), [title])`로 짰는데 `react-hooks/set-state-in-effect`
린트 에러가 났다("effect 안에서 동기적으로 setState하면 렌더가 한 번 더 낀다"). → React
문서가 권하는 "렌더 중 이전 값과 비교해 즉시 갱신" 패턴(`if (title !== prevTitle) {
setPrevTitle(title); setPeeked(false); }`)으로 바꿔 해결. **prop 변화에 맞춰 state를
리셋하는 건 흔한 패턴이라 useEffect가 먼저 떠오르지만, React 최신 권장은 렌더 중 비교다.**

### 색·폰트는 값이 확정되기 전에도 토큰 참조로만 짠다 (8/11, 신규 — 팀 차원 규칙)

`tokens.css`의 현재 값이 진짜 최종값인지 확인 없이 리터럴로 박으면, 나중에 값이 바뀔 때
전체를 다시 훑어야 한다. **값이 아직 정해지지 않았어도(심지어 "확실히 또 바뀐다"는 걸
알아도) 토큰 이름으로 참조해두면, 소유자가 값만 바꿔도 자동으로 따라간다.** 이번 감사에서
8/11에 추가한 코드는 전부 이미 이 규칙을 지키고 있었던 것도 확인됨 — 규칙을 알기 전부터
습관적으로 지켜온 셈이라 오히려 감사가 쉬웠다.

**→ 시험 병합 + 빌드로 확인한다.**

### (기존) "커밋됐다"와 "병합됐다"는 다른 말이다

**→ diff·stat만으로 "병합됐다"고 판단하지 않는다.**

### (기존) 남의 브랜치가 통째로 자라난 파일은 패치가 아니라 교체로 받는다

### 상태 신뢰 원칙 (기획서 §설계원칙 5, 파트 C가 지키는 규칙 — 유지)

- 서버가 단일 진실 공급원 — 화면은 상태를 소유하지 않고 그리기만 한다
- `GameState`는 매번 통째로 온다 — 증분 반영 로직이 없다 (`setState(e.state)` 한 줄)
- 타이머는 `deadlineAt`(절대 시각)만 받아 매 틱 `deadlineAt - Date.now()`로 재계산한다
- 과반·투표자 수는 전부 `players.length`에서 계산한다 — 인원수 하드코딩 없음
- `isBot`·`role`은 애초에 `GameState`에 없다 — 서버 `view.ts`가 한 곳에서 걸러 보낸다

## 12. 핵심 코드 리뷰

> 발표용 구조(맥락/문제 → 대안 → 선택+근거 → 효과)로 정리. 근거 상세는 4절과 대응한다.

### ① `myId` 필드 발견 — 계약의 명백한 누락을 화면을 그리다 찾아냄

- **맥락/문제**: `GameState`에 "지금 내 차례인가"를 판단할 방법이 없었다.
- **대안**: (a) join 응답에 별도 필드로. (b) `GameState`에 필드로.
- **선택 + 근거**: (b). 서버가 단일 진실 공급원이라는 원칙과 맞는다.
- **효과**: `myId` 포함 ★1~★6, v2.0 계약 신규 필드 대부분이 이 경로로 나왔다.

### ② 라벨 익명화 — 서버 한 곳에서 막지 않으면 어디서든 샌다

- **맥락/문제**: `label`은 봇 판별 단서 차단 목적인데, `stateMachine.ts`의 시스템 메시지가
  실명을 계속 썼다.
- **선택 + 근거**: 익명화 책임을 지닌 `view.ts` 한 곳으로 모든 출구를 통일.
- **효과**: `.label`로 수정, 이후 `botVoteResults` 등도 같은 게이팅 패턴을 따름.

### ③ ★7(`returnReason` 필드) 기각 — 필드로 못 담는 정보는 필드로 만들지 않는다

- **맥락/문제**: 동점 재투표 vs "살린다" 복귀, `phase`만으론 구분 불가.
- **선택 + 근거**: 서버 시스템 메시지 문장으로 전달, 필드 추가 안 함 — 대상이 들어간 문장은
  필드로 표현 불가.
- **효과**: 계약 필드 안 늘고, 두 경로 화면 구조가 완전 동일해짐.

### ④ `Reveal`의 `liarGameResult` 항상 `null` — 결과 은닉도 스포일러가 될 수 있다

- **선택 + 근거**: 라이어 적발 케이스만 숨기면 "결과가 안 뜬다"는 사실 자체가 스포일러.
  항상 `null`로 미루고 `result`에서만 채움.
- **효과**: `view.ts`가 이중 방어(예약값 → result 전이에서만 이관 → 다시 null 감쌈).

### ⑤ botVote를 별도 화면이 아니라 채팅 화면의 팝업으로 흡수 (8/11, 신규)

- **맥락/문제**: 2차 테스트에서 "봇 지목할 때 우리가 했던 말을 같이 보고 싶다"는 요청이
  나왔다. 기존엔 봇 지목이 파트 D의 완전히 별도인 전체화면(`VoteScreen.tsx`)이라 채팅
  로그에 접근할 방법 자체가 없었다.
- **대안**: (a) `VoteScreen`에 채팅 로그를 별도로 그려 넣는다 — 두 화면이 각자 채팅 렌더링
  로직을 갖게 되어 중복·불일치 위험. (b) botVote를 채팅 화면(`MainScreen`)의 팝업 체계로
  옮긴다 — 이미 있는 `MainScreen`(항상 채팅이 떠 있음) 위에 얹기만 하면 됨.
- **선택 + 근거**: (b). 기획서 v3.0이 이 방향으로 소유 자체를 D→C로 옮겼다. 팝업 체계
  (`modalFor`)에 케이스 하나 추가하는 것만으로 "채팅이 항상 보인다"는 요구사항이 자동
  충족된다 — 새로 만들 게 아니라 이미 있는 구조에 얹은 것.
- **효과**: 화면이 하나 줄고(별도 `VoteScreen` 삭제), 다른 4개 팝업과 완전히 같은 패턴
  (`{state, onEvent}`, 즉시-반영)을 따르게 되어 화면 체계 전체의 일관성이 올라감.

### ⑥ 팝업 스크림을 전체 화면에서 채팅 로그 영역으로 축소 (8/11, 신규)

- **맥락/문제**: 기존엔 팝업이 뜨면 투표 패널·입력창까지 전부 어두운 스크림으로 덮여
  안 보였다. 시안 1이 이걸 "채팅 영역만 덮기"로 다시 설계했고, 실 구현에도 반영 요청받음.
- **대안**: (a) 팝업을 여전히 전역에 두되 z-index/투명도만 조정 — 여전히 투표 패널이
  덮인다. (b) 팝업을 DOM 상 채팅 로그 컨테이너 안으로 옮기고 그 컨테이너 기준으로
  절대 위치.
- **선택 + 근거**: (b). CSS만으로 "일부 영역만 덮기"를 구현하려면 실제로 그 영역의 자식이
  되어야 한다 — 부모가 다르면 아무리 좌표를 맞춰도 반응형에서 깨진다.
- **효과**: 투표 패널·입력창이 팝업 중에도 계속 보이고 조작 가능해짐(단 입력은 별도로
  잠김, 4절 #17). 부가로 ✕(잠깐 접기)+재오픈 칩까지 자연스럽게 같은 컨테이너 안에서
  구현됨(10절 CSS 기법 참고).
