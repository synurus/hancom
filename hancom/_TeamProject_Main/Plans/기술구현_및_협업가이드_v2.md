# 기술 구현 및 협업 가이드 v2

> v1 대비 변경사항: 배포 구조를 프론트/백엔드 분리(Vercel+Railway)에서 **Railway 단일 배포**로 통합. LLM 모델을 gpt-4.1-mini로 확정. 기획서는 `봇과함께하는라이어게임_기획_v5.md` 참고.

## A. 기술 스택

| 항목 | 결정 | 근거 |
|---|---|---|
| 프론트엔드 | **Vite + React** | 수익 모델(광고)이 빠지면서 Next.js의 SEO/SSR 이점이 약해졌고, 1주 MVP·3주 전체 일정엔 가벼운 조합이 안전 |
| 백엔드 | **Express + Socket.IO** | WebSocket 필수. Socket.IO는 room 개념이 내장돼 있어 "방" 단위 구조와 잘 맞고 재연결 처리를 직접 구현할 필요가 없음 |
| DB | **Postgres (Supabase)** | 리플레이 로그, 구조화 상태 저장소, 관전자=판별자 봇이 읽을 데이터가 게임 종료 후에도 남아야 해서 영속 저장소 필수 |
| **배포** | **Railway 단일 배포** (변경) | Vite+React는 빌드하면 정적 파일 묶음이라, Express가 `express.static`으로 직접 서빙 가능. Socket.IO 서버와 프론트 정적 파일을 같은 Railway 서비스 하나에 올려서 배포 파이프라인 1개, 도메인 1개, CORS 설정 불필요. Vercel은 사용하지 않음 — Next.js가 아니라 순수 SPA인 데다 SEO를 살릴 이유(광고)도 없어져서 분리 배포의 이점이 사라짐 |
| 언어 | **TypeScript** | WebSocket 메시지 스키마, 게임 상태(`liarId`, `remainingTurns` 등)를 프론트-백엔드가 공유해야 해서 컴파일 타임 검증 이득이 큼 |

## B. LLM / API

- **프로바이더**: OpenAI (구독 또는 API 토큰), 1개로 시작 (멀티 프로바이더는 포스트-MVP)
- **모델**: **gpt-4.1-mini** — gpt-4o-mini 대비 단가는 살짝 높지만 이 규모(게임당 1원 미만)에선 차이가 무의미하고, 더 최신 세대라 자연스러움·지시 이행력이 나음
- **예상 비용**: 게임 1판당(봇 발언 ~7회 + 관전자봇 분석 1회) 1원 미만. 버그로 인한 API 폭주 방지용으로 월 예산 상한 $20~30 설정 권장
- **Honcho**: MVP·1차 개발 범위에서는 제외

## D. 팀 역할 분담

| 팀원 | 담당 | 비고 |
|---|---|---|
| 유민성 | 백엔드 전체 (Express+Socket.IO 서버, 라이어게임 룰 엔진 상태머신, 발언권/시간 관리, DB 연동, **Railway 배포/정적 파일 서빙 설정**) | 풀스택 + 웹소켓 지식 보유 |
| 김정현 | AI/LLM 전체 (참여봇 프롬프트 — 라이어/일반 분기 포함, 관전자=판별자 봇, 오픈소스 AI 감지 도구 연동) | |
| 이현우 | 프론트엔드 — 게임 화면 (채팅 UI, 실시간 상태 표시, 투표 UI) | 로직 자체는 백엔드가 소스, 이현우는 그걸 화면에 반영하는 역할로 경계 설정 |
| 박진 | 프론트엔드 — 레이아웃/디자인 시스템 (랜딩페이지, 방 생성/입장 화면, 전체 비주얼) | |

이현우/박진 둘 다 프론트엔드라 컴포넌트 경계(게임 화면 컴포넌트 vs 공용 UI/디자인 토큰)를 1주차에 미리 정해두는 걸 권장. 배포가 Railway 하나로 통합되면서 별도 Vercel 설정 작업이 사라져, 유민성의 배포 작업 범위가 "Railway에 Express 정적 서빙 + Socket.IO 세팅" 하나로 단순해짐.

**파트 구조**: 4개 파트 확정 (개인이 맡을 수 있는 범위를 극대화하는 방향)

## F. 협업 규칙

**브랜치 전략**: `main` + `dev` + `feat/<파트명>` (4인 규모엔 정식 git-flow는 과함)
- `feat/<파트명>`에서 각자 작업 → PR로 `dev`에 머지(리뷰 후) → 마일스톤 단위로 `dev` → `main` 머지
- `main`은 항상 "지금 시연 가능한 상태"만 유지

**PR 리뷰**: 최소 1명이 훑어보고 머지하는 라이트 리뷰. 급할 땐 본인이 머지하되 Discord에 알림 남기기

**린터**: ESLint/Prettier 사용 권장 — TS와 함께 팀원 간 스타일 차이를 자동으로 정리

**이슈 트래킹**: GitHub Issues + Discord 병행. Discord는 실시간 소통, GitHub Issues는 진행 상황 추적용
