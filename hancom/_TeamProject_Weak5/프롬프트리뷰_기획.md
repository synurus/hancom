# prompt-review — 지시문을 되돌아보는 시스템

> 5주차 평가 항목 **"AI를 잘 쓰고 있는가"** 에 대한 우리 팀의 답.

---

## 1. 문제 — 우리는 결과물만 봤지 지시문은 한 번도 안 봤다

1주차부터 4주차까지 우리가 만든 것을 나열하면 이렇게 된다.

| 주차 | 시스템 | 다룬 것 |
|---|---|---|
| 1주차 | 회의록 자동화 | 회의 **기록** |
| 2주차 | `/알려주기` | 배운 **개념** |
| 3주차 | `/codebook` | 남의 **코드** |
| 4주차 | `/cleanflow` | 우리 **코드의 배치** |

**넷 다 산출물을 다뤘다.** 그런데 그 산출물은 전부 사람이 AI에게 지시해서 나왔다. 회의록도, 코드북도, cleanflow 의 재배치도, 심지어 이 시스템들을 만든 스킬 자체도 그렇다.

```
지시문  ──▶  AI  ──▶  산출물
  ▲                     ▲
  │                     │
아무도 안 봄        1~4주차가 전부 여기
```

**같은 도구를 쥐어줘도 결과가 사람마다 다르다.** 그 차이는 도구가 아니라 지시문에서 난다. 그런데 우리는 그걸 한 번도 들여다본 적이 없다.

### 로그는 이미 쌓이고 있다

AI 코딩 도구는 대화를 통째로 로컬에 남긴다.

```
~/.claude/projects/<프로젝트별 폴더>/<세션ID>.jsonl
```

**한 세션이 수 MB씩 쌓인다.** 사람이 친 프롬프트, AI 응답, 도구 호출 결과, 붙여넣은 이미지가 전부 들어 있다. 우리 넷 모두 몇 주치를 갖고 있다.

**그리고 아무도 열어본 적이 없다.**

### 3주차와 똑같은 구조의 문제

3주차 기획서의 문장을 그대로 가져올 수 있다.

> "리뷰를 안 한 게 아니라, **남의 코드를 읽을 진입로가 없었다**."

프롬프트도 같다. 남이 어떻게 지시하는지 볼 방법이 없다. **다른 점은 하나 — 코드는 저장소에 있어서 마음만 먹으면 읽을 수 있지만, 로그는 각자 PC 안에만 있다.** 진입로가 없는 정도가 아니라 아예 닫혀 있다.

---

## 2. 왜 "프롬프팅 잘하는 법" 문서로는 안 되는가

검색하면 나오는 팁 목록은 이미 많다. 그게 안 먹히는 이유는 3주차가 첫 시안(`llm.ts` 코드북)을 폐기했던 이유와 똑같다.

| | 일반 프롬프팅 가이드 | 우리에게 필요한 것 |
|---|---|---|
| 근거 | 일반론 — "구체적으로 쓰세요" | **내가 실제로 어디서 되돌아갔는지** |
| 대상 | 누구에게나 해당 | 내 습관, 이 프로젝트의 맥락 |
| 검증 | 없음 | **로그에 다 남아 있다** |
| 읽고 나면 | 고개를 끄덕이고 잊는다 | 다음 세션에서 확인 가능 |

*"구체적으로 쓰세요"* 는 3주차가 폐기한 *"SDK란 무엇인가"* 와 같은 말이다. **틀리진 않았는데 아무것도 안 바꾼다.**

바꾸려면 *"12번 프롬프트에서 대상 파일을 안 적어서 13번에서 다시 잡았다"* 처럼 **자기 로그에서 나온 문장**이어야 한다. 그건 검색으로 안 나오고, 로그를 읽어야만 나온다.

---

## 3. 정의 — 우리에게 좋은 프롬프트란

> **같은 결과를 더 적은 왕복으로 얻는 지시문.**

이 정의를 고른 이유는 4주차와 같다. **확인 가능**하기 때문이다. "좋은 프롬프트"나 "명확한 지시"는 판정할 방법이 없지만, 왕복 횟수는 로그에 그대로 남아 있다.

여기서 두 가지가 따라 나온다.

```
① 짧은 게 좋은 것도, 긴 게 좋은 것도 아니다   → 왕복이 줄었는가만 본다
② 판정은 결과가 아니라 과정에서 나온다        → 결국 원하는 걸 얻었어도
                                                 세 번 되돌아갔으면 개선 여지다
```

②가 중요하다. **대부분의 세션은 결국 성공한다.** AI 가 못 알아들으면 사람이 다시 말해주기 때문이다. 그래서 결과만 보면 전부 잘한 것처럼 보이고, 개선점은 **되돌아간 횟수에만** 드러난다.

---

## 4. 무엇을 보는가 — 재작업 사슬

핵심 재료는 하나다.

```
N번   지시
        ↓
      결과가 어긋남
        ↓
N+1번 "아니 그게 아니라 …"     ← 여기가 아니라
        ↓
      N번에 무엇이 빠져 있었나   ← 여기가 리포트의 재료다
```

**고쳐야 할 것은 N+1번이 아니라 N번이다.** N+1번은 이미 잘 쓴 프롬프트인 경우가 많다 — 한 번 어긋나고 나면 사람은 저절로 구체적으로 말하기 때문이다. **그 구체성을 처음부터 쓰게 하는 것**이 이 시스템의 전부다.

### 우리가 실제로 보는 패턴 5가지

| 패턴 | 무엇이 빠졌나 |
|---|---|
| **맥락 없는 지시대명사** | "이거", "그 파일", "아까 그거" — 로그만 봐서는 무엇인지 특정이 안 된다 |
| **여러 요구 한 덩어리** | 한 프롬프트에 요구가 셋. 하나만 처리되고 나머지가 흘러간다 |
| **성공 기준 부재** | "고쳐줘", "잘 되게 해줘" — 무엇이 통과인지가 없다 |
| **거대 붙여넣기 + "봐줘"** | 수천 자를 던지고 어디를 봐야 하는지는 안 준다 |
| **금지 없는 요청** | 하지 말아야 할 것을 안 적어서 안 건드려도 될 곳까지 바뀐다 |

**이 목록은 고정이 아니다.** 로그를 읽다 새 패턴이 나오면 그걸 쓴다. 위 다섯은 자주 나오는 것일 뿐이고, **목록에 맞추려고 없는 패턴을 만들어내는 것이 이 시스템의 가장 큰 실패 방식**이다.

## 5. 규칙

### 5-1. 원문 인용 없는 지적은 쓰지 않는다

모든 지적에 **몇 번 프롬프트인지와 실제 문장**이 붙는다. 이건 4주차가 추정 주석에 `※ 소유자 확인 필요` 를 붙인 것과 같은 장치다.

> LLM은 그럴듯한 이유를 만들어내는 데 능하다.  — 4주차 시스템 설계도 §6

프롬프트 분석은 이 위험이 더 크다. 사람의 습관에 대해서는 **아무 말이나 해도 그럴듯하게 들리기 때문**이다. 원문 인용이 그걸 막는 유일한 장치다.

### 5-2. 기계적 신호는 단서지 결론이 아니다

추출 단계에서 숫자가 몇 개 나온다 — 프롬프트 수, 길이 중앙값, 단문 비율, 되돌리기 신호어 수. **이건 어디를 먼저 읽을지 정하는 데만 쓴다.**

```
"20자 미만이 15%"     →  짧아서 나쁜 게 아니다.
                          연속 대화 중의 "응 그렇게 해"는 짧은 게 맞다
"되돌리기 신호어 7개"  →  "아니"가 들어갔다고 다 재지시가 아니다.
                          "아니면 이 방법은?" 같은 것이 섞인다
```

**숫자만 보고 리포트를 쓰면 전부 오탐이 된다.** 반드시 프롬프트 전문을 읽고 판단한다.

### 5-3. 잘 된 것을 최소 하나 찾는다

지적만 나열한 리포트는 읽히지 않는다. 그리고 **잘 통한 프롬프트가 개선안의 재료**다 — 같은 사람이 이미 쓸 줄 아는 형식이라, "이렇게 쓰세요"보다 "3번처럼 쓰세요"가 훨씬 잘 먹힌다.

### 5-4. 사람이 아니라 패턴을 지적한다

```
✕  "성의 없이 던졌다"
○  "대상 파일이 빠져 있었다"
```

리포트를 본인이 읽는다는 걸 잊지 않는다.

### 가장 중요한 원칙

> **리포트는 "고쳐라"보다 "이건 잘 통했다"를 말할 수 있어야 한다.**

4주차의 *"규칙은 고쳐라보다 이 파일은 됐다를 더 자주 말할 수 있어야 한다"* 와 같다. 무슨 로그를 넣어도 지적이 열 개씩 나온다면, 그건 분석이 아니라 **트집을 생성하는 기계**다.

## 6. 파이프라인 — 선택 → 추출 → 분석 → 활용

4주차와 같은 네 단계다. **②를 건너뛸 수 없다는 것이 이 시스템의 기술적 핵심**이다.

### ① 선택 — 어느 세션인가

로그는 사람마다 다른 절대경로에 있다. **경로를 하드코딩하면 만든 사람만 쓸 수 있는 스킬이 된다.** 그래서 매번 찾는다.

```
· ~/.claude/projects/ 전체를 훑는다
· 용량 내림차순으로 정렬한다
· 기본값은 가장 큰 것 하나
```

**용량이 큰 세션 = 오래 굴린 세션 = 습관이 가장 많이 드러나는 세션.** 그리고 한 번에 하나만 본다 — 리포트는 세션당 하나다.

### ② 추출 — 사람이 친 것만 남긴다

로그를 통째로 읽는 건 **불가능하다.** 한 세션이 10MB 를 넘고, 그 대부분은 사람이 쓴 글이 아니다.

| 로그에 든 것 | 프롬프트 분석에 | 비고 |
|---|---|---|
| 사람이 친 프롬프트 | **필요** | 이것만 있으면 된다 |
| AI 응답 | 불필요 | 분석 대상이 아니다 |
| 도구 호출 결과 | 불필요 | 파일 내용·명령 출력이 통째로 들어 있다 |
| 붙여넣은 이미지 | 불필요 | base64 라 **용량의 대부분을 차지한다** |
| 시스템·훅 주입 메시지 | 불필요 | 사람이 쓴 것처럼 보이지만 아니다 |

마지막 줄이 함정이다. 로그에서 `user` 로 표시된 것 중 상당수는 **사람이 친 게 아니다** — 도구 결과, 훅 출력, 자동 주입 알림이 전부 같은 자리에 들어간다. 이걸 안 거르면 리포트가 "사용자가 파일 내용을 그대로 붙여넣었다" 같은 헛소리를 하게 된다.

```
10 MB 로그  ──필터──▶  7 KB 다이제스트
                       (프롬프트 수십 개 + 기계적 신호)
```

**여기까지가 기계의 일이다.** 판단은 하나도 안 한다.

### ③ 분석 — 다이제스트를 읽는다

재작업 사슬을 따라가며 §4의 패턴을 찾는다. 각 지적마다 원문을 인용하고, **그 세션의 실제 맥락으로** 고쳐 쓴 예시를 붙인다.

### ④ 활용 — 다음 세션에서 달라졌는지 본다

```
· 리포트의 체크리스트를 다음 세션에서 실제로 써본다
· 며칠 뒤 그 세션을 다시 돌린다
· 되돌리기 신호어 수가 줄었는가
```

**여기까지 해야 한 바퀴다.** 4주차가 *"정리해놓고 안 써보면 그 배치가 쓸 만한지 알 수 없다"* 고 한 것과 같다. 리포트를 읽고 끝내면 일반 프롬프팅 가이드와 다를 게 없어진다.

## 7. 운영 — 여기서만 다른 점

3·4주차 시스템은 전부 이 모양이었다.

```
디스코드에서 봇 멘션  →  저장소에 PR  →  팀 전체가 본다
```

**prompt-review 는 이 흐름을 못 쓴다.** 이유가 둘이다.

| | 왜 |
|---|---|
| **로그가 로컬에만 있다** | 봇이 남의 PC 안을 못 읽는다. 각자 자기 자리에서 돌려야 한다 |
| **로그에 사적인 것이 섞인다** | 시행착오, 혼잣말, 다른 프로젝트 이야기가 그대로 들어 있다 |

그래서 이렇게 한다.

```
① 각자 자기 PC 에서 돌린다      /prompt-review
② 리포트는 로컬에 저장된다      ~/Downloads/[프로젝트]_[세션ID]_개선점.md
③ 공유 여부는 본인이 정한다     저장소에 자동으로 올라가지 않는다
④ 팀에는 패턴만 가져온다        원문 인용 없이 "이런 습관이 있더라" 만
```

**③이 이 시스템의 성격을 정한다.** 3·4주차는 산출물을 저장소에 올리는 게 당연했지만, 여기서는 **자동 공개가 기본값이면 아무도 안 돌린다.** 자기 시행착오가 그대로 팀에 보이는 걸 감수하면서까지 돌릴 사람은 없다.

### 그래도 팀에 남는 것

개인 리포트는 각자 갖되, **넷의 리포트에서 같은 패턴이 나오면 그건 팀 규칙이 된다.**

```
넷 중 셋이 "대상 파일 안 적음"으로 되돌아갔다
        ↓
그건 개인 습관이 아니라 우리 프로젝트의 구조 문제일 수 있다
  (파일이 많고 이름이 비슷해서 "그 파일"로 부르게 된다)
        ↓
3주차 파일트리.md 처럼 경로를 붙여넣기 쉽게 만드는 쪽이 답일 수도 있다
```

**개인 교정으로 시작해서 팀 규칙으로 끝난다.** 이게 5주차가 개인 과제가 아닌 이유다.

## 8. 시스템 — 스킬로 만든다

`/prompt-review` — 파이프라인 ①~③ 을 수행하고 리포트를 저장한다. ④ 는 사람이 한다.

```
~/.claude/skills/prompt-review/
  SKILL.md                  분석 관점 · 리포트 형식 · 규칙
  scripts/extract_prompts.py  로그 탐색 + 프롬프트 추출
```

**판단하는 부분과 기계적인 부분을 파일로 갈라놓았다.** 4주차가 커밋을 이동/주석으로 쪼갠 것과 같은 이유다 — 섞으면 어디까지가 사실이고 어디부터가 해석인지 알 수 없어진다.

| | 스크립트 | SKILL.md |
|---|---|---|
| 하는 일 | 찾고 · 거르고 · 센다 | 읽고 · 판단하고 · 쓴다 |
| 틀리면 | 숫자가 어긋난다 (확인 가능) | 리포트가 헛소리가 된다 |
| 그래서 | 규칙을 코드로 고정 | 규칙을 문서로 고정 (§5) |

### 리포트 형식

```
한 줄 요약        이 세션의 프롬프팅을 한 문장으로
잘 통한 것        원문 인용 + 왜 통했는지          (최소 1개)
아쉬운 점         원문 인용 + 무슨 일이 있었는지
                  + "이렇게 썼다면" 재작성 예시    (3~5개)
추천 말투         지금 말투 → 추천 말투 표
                  (왼쪽은 세션에 실제로 나온 것만)
다음 세션 체크리스트  이 세션에서 실제로 걸린 것만
```

**항목 수보다 정확도다.** 아쉬운 점 3개짜리 리포트가 12개짜리보다 낫다.

### 아무것도 하지 않는 경우

- **세션이 너무 짧다** → 습관이 안 드러난다. "이 세션은 표본이 부족합니다"
- **되돌아간 곳이 없다** → "이 세션은 됐습니다"로 끝낸다. 억지로 지적을 만들지 않는다
- **근거를 못 찾겠다** → 그 패턴은 안 쓴다. 추측으로 채우지 않는다

3·4주차와 같다. **아무것도 안 하고 끝나는 것이 정상 결과 중 하나다.**

## 9. 산출물

```
5주차/
  시스템/   기획 · 시스템 설계도 · 유저 시나리오 · SKILL.md · 시연 영상 · 발표자료
```

**3주차 `코드북/`·4주차 `정리기록/` 과 달리 기록 폴더를 두지 않는다.** 리포트는 개인 로컬(`~/Downloads/`)에 남고, 공유 여부는 본인이 정하기 때문이다(§7). 이 폴더에는 **방법만** 남긴다.

## 10. 이 방식을 고른 이유

**대안과 비교했을 때.**

| 방식 | 문제 |
|---|---|
| 프롬프팅 가이드 문서 작성 | 일반론이 된다. 3주차가 폐기한 첫 시안과 같은 실패 |
| 서로의 화면을 보며 페어 프롬프팅 | 넷의 시간을 맞춰야 한다. 그리고 남이 볼 때는 평소처럼 안 친다 |
| 잘 된 프롬프트만 모아 공유 | 성공 사례만 남는다. **개선점은 실패한 왕복에만 있다** |
| 로그를 통째로 AI 에게 읽히기 | 10MB 를 넘는다. 대부분이 이미지·도구 출력이라 읽히지도 않는다 |
| **로그 추출 + 사건 기반 리뷰 (채택)** | 이미 쌓여 있는 데이터를 쓴다. 근거가 전부 원문 인용이라 반박 가능하다 |
