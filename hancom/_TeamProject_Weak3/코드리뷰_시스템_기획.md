# 코드북 — 코드 리뷰 시스템 기획

> 3주차 평가 항목 **"코드를 이해할 수 있는가?"** 에 대한 우리 팀의 답.

---

## 1. 문제

4명이 파트를 나눠 개발하면서 **각자 자기 코드만 아는 상태**가 됐다. 실제로 있었던 일들이다.

| 언제 | 무슨 일 |
|---|---|
| 8/11 | 박진이 "뭔가 없어서 공용 컴포넌트를 못 만들겠다"고 함 — 실제로는 테마 결정권이 자기에게 있다는 걸 몰랐던 것 |
| 8/12 | 유민성이 `knowledge.ts`를 독립적으로 만듦 — 봇 쪽에서 같은 기능을 이미 검토하고 보류한 걸 몰랐던 것 |
| 8/12 | PR 12개 중 리뷰가 달린 것은 **1개뿐** |

**"리뷰를 안 한 게 아니라, 남의 코드를 읽을 진입로가 없었다."**

## 2. 왜 일반적인 코드 리뷰로는 부족한가

PR 리뷰는 **바뀐 줄(diff)만** 보여준다. 그런데 우리가 겪은 문제는 *"이 파일이 애초에 뭘 하는 파일인지"* 를 모르는 것이었다. diff만 봐서는 그게 안 채워진다.

그리고 팀원마다 아는 것이 다르다.

```
이현우   프론트는 밝고 백엔드는 덜함
유민성   DB·서버는 밝고 프론트는 덜함
박진     화면은 밝고 상태관리·소켓은 덜함
김정현   봇·계약은 밝고 화면 구현은 덜함
```

**한 줄짜리 설명 문서는 한 명을 지루하게 하고 다른 한 명을 놓친다.**

## 3. 해결 — 분기형 코드북

읽는 사람의 수준에 따라 **경로가 갈리는 문서**를 파일마다 하나씩 만든다. 게임북(텍스트 어드벤처)과 같은 방식이다.

```
1번  "봇이 서버 안에서 도는지 밖에서 도는지 아시나요?"
       예   → 6번 (구조부터)
       아니오 → 2번 (짧은 설명을 거쳐 6번으로)
```

**아는 사람은 4단계, 처음인 사람은 12단계를 거치지만 도착점은 같다.**

### 핵심 원칙

| 원칙 | 이유 |
|---|---|
| **ZETEO 안에서만 성립하는 설명** | "SDK란 무엇인가"는 검색하면 나온다. 우리가 써야 할 것은 "이 함수가 게임의 어느 순간에 불리는가" |
| **연결을 설명한다** | 파일 하나를 이해하는 게 목적이 아니라, 그 파일이 다른 파일·전체 흐름과 어떻게 물리는지가 목적 |
| **도착점 명시** | 마지막 노드에 "이제 설명할 수 있는 것" 목록. 평가 항목과 직접 대응 |
| **깨지면 어떻게 되는가** | 그 코드가 없거나 잘못되면 게임에서 무슨 일이 벌어지는지 |
| **빠른 경로도 내용은 안 건너뛴다** | 건너뛰는 것은 *선행 개념 설명*이지 *코드*가 아니다. 아는 사람도 그 파일의 핵심은 전부 보고 지나간다 |

### 첫 시안을 폐기한 이유

`llm.ts` 로 만든 첫 코드북은 **버렸다.** 노드도 분기도 형식은 갖췄는데 읽어보니 이랬다.

```
❌ "SDK란 무엇인가" · "지연 초기화 패턴이란" · "환경변수를 쓰는 이유"
      → 이 파일이 없어도 성립하는 글이었다
```

**일반 프로그래밍 튜토리얼에 우리 파일을 예제로 끼워넣은 꼴**이었다. 다 읽어도 *"이 코드가 ZETEO에서 무슨 역할인지"* 는 여전히 모른다.

그래서 노드 구성을 바꿨다.

```
이전   개념 설명 → 개념 설명 → ... → 마지막에 연결 표 한 줄
이후   전체 그림에서의 위치 → 누가 언제 부르는가 → 핵심 함수들
       → 깨지면 무슨 일이 → 바깥과의 계약 → 도착
```

분기 질문의 기준도 바꿨다.

```
❌ "SDK 써보셨나요?"                     일반 지식
✅ "봇이 서버 안에서 도는지 아시나요?"    ZETEO 지식
```

## 4. 운영 방식

```
① 디스코드 #code-book 채널 핀 메시지에 파일 트리(메뉴판)
② 읽고 싶은 파일 경로를 채팅에 적는다
③ 김정현이 모아서 코드북 생성 → TeamB 저장소에 커밋
④ 읽은 사람이 "이제 ___를 설명할 수 있습니다" 한 줄 남긴다
⑤ 막힌 노드 번호를 적으면 그 노드를 쪼개서 개선
```

**④가 이 시스템의 증거다.** 문서를 AI가 썼더라도, *"A가 X를 몰랐는데 이제 설명할 수 있다"* 는 사람의 기록이다.

### 자동화 — `/codebook` 스킬

③을 매번 손으로 하면 품질이 들쭉날쭉해진다. 생성 규칙을 스킬(`~/.claude/skills/codebook/`)에 고정해 두었다.

**설계에서 가장 어려웠던 지점은 "맥락 전달"이었다.**

코드만 읽어서는 *왜* 그렇게 짰는지 알 수 없다. 그러면 *"SDK란 무엇인가"* 같은 검색하면 나오는 글이 만들어진다. 실제로 첫 시안(`llm.ts`)이 그렇게 나와서 폐기했다.

그래서 스킬에 **0단계 — 배경 지식을 먼저 채운다**를 넣었다.

| 넣은 것 | 없으면 못 쓰는 것 |
|---|---|
| 설계원칙 5 | `view.ts`가 왜 유일한 관문인지 |
| 파트 분담표 | 누가 왜 이 파일을 만들었는지 |
| 구조 요약 (화면 5개·게임 흐름·루프 2개) | 이 파일이 게임의 어느 순간에 동작하는지 |
| **코드 모양을 결정한 실제 사건 6건** | 왜 이 방어 코드가 존재하는지 |

마지막이 특히 중요하다. 예를 들어 **"프롬프트는 경향을 만들 뿐 보장하지 않는다"** — 봇의 제시어 유출을 프롬프트로 두 번 막았다가 두 번 다 뚫린 뒤 얻은 결론인데, **이 문장은 코드 어디에도 적혀 있지 않다.** 그런데 이걸 모르면 `bot/index.ts`의 검사 4종이 왜 있는지 설명할 수 없다.

## 6. 이 방식을 고른 이유

**대안과 비교했을 때.**

| 방식 | 문제 |
|---|---|
| 각자 문서 하나씩 작성 | 발표까지 6일. 팀원이 반나절씩 쓸 시간이 없다 |
| PR 리뷰만 강화 | 남은 PR이 적어 증거가 안 쌓인다. diff만으로는 파일 전체를 이해 못 한다 |
| 전체 아키텍처 문서 하나 | 수준 차이를 흡수 못 한다. 길면 아무도 안 읽는다 |
| **분기형 코드북 (채택)** | 팀원은 경로 한 줄만 적으면 된다. 수요가 있는 파일만 만들어 낭비가 없다 |
