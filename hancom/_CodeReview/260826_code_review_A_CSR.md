CSR (Client-Side Rendering)이란?

서버는 최소한의 HTML 뼈대만 내려주고, 실제 화면 콘텐츠는 브라우저(클라이언트)에서 JavaScript가 실행되면서 그려지는 렌더링 방식입니다.

서버 응답: <div id="root"></div> + JS 파일 하나
브라우저: JS를 다운로드 → 실행 → 그제야 화면에 실제 콘텐츠가 그려짐

React, Vue 같은 라이브러리로 만든 SPA가 기본적으로 이 방식으로 동작합니다. (SPA가 "무엇을 다시 그리는가"에 대한 개념이라면, CSR은 "누가 그리는가"에 대한 개념이라고 보면 됩니다. 둘은 짝을 이루는 경우가 많아요.)

장점

페이지 전환이 빠르고 매끄러움

최초 로딩 이후엔 서버에 새 HTML을 요청하지 않고, 필요한 데이터(JSON)만 받아서 JS가 화면 일부만 바꿔 그립니다. 그래서 페이지 이동 시 깜빡임 없이 앱처럼 부드럽게 동작합니다.

서버 부하가 적음

서버는 매번 완성된 HTML을 렌더링해서 보내는 대신, 정적 파일(HTML 뼈대, JS)과 API(JSON)만 제공하면 됩니다. 렌더링(그림 그리는 일)의 부담이 서버가 아니라 사용자의 브라우저로 넘어갑니다.

상호작용이 풍부한 UI에 적합

드래그, 실시간 필터링, 애니메이션처럼 화면이 자주 바뀌는 기능을 서버 왕복 없이 클라이언트에서 즉시 처리할 수 있습니다.

프론트/백엔드 역할 분리가 명확함

프론트는 화면 렌더링, 백엔드는 데이터(API) 제공에만 집중할 수 있어 개발 구조가 깔끔해집니다.
단점

초기 로딩이 느림

사용자가 첫 화면을 보기까지 "JS 파일 다운로드 → 파싱 → 실행 → 렌더링" 과정을 다 거쳐야 합니다. 그동안 화면은 빈 화면이거나 로딩 스피너만 보이는 경우가 많습니다. 특히 JS 번들이 크거나 사용자의 인터넷/기기 성능이 안 좋으면 이 공백이 눈에 띄게 길어집니다.

SEO(검색엔진 최적화)에 불리함

검색엔진 크롤러가 서버로부터 처음 받는 HTML에는 실제 콘텐츠가 비어있고, JS가 실행돼야 콘텐츠가 채워집니다. 크롤러가 JS 실행을 제대로 못 하거나 타임아웃되면 콘텐츠를 못 읽어서 검색 노출이 잘 안 될 수 있습니다.

저사양 기기/느린 네트워크에서 불리함

렌더링 부담이 서버가 아니라 사용자의 브라우저(기기)로 넘어가기 때문에, 사용자의 기기 성능이나 네트워크 환경이 나쁘면 그 부담을 그대로 사용자가 떠안게 됩니다.

보안상 노출 위험

화면을 그리는 로직과 데이터 처리 흐름이 클라이언트(브라우저)에 다운로드된 JS 코드 안에 있기 때문에, 민감한 로직을 클라이언트에 두면 사용자가 개발자도구로 코드를 들여다볼 수 있습니다.
