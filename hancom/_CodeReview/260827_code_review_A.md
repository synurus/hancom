SSR (Server-Side Rendering)이란?

SSR은 브라우저가 아니라 서버에서 먼저 HTML을 완성한 뒤, 그 완성된 HTML을 클라이언트에 내려주는 렌더링 방식입니다.

SPA(CSR)와 비교하면 이해가 쉬워요

CSR (Client-Side Rendering) — 일반적인 SPA 방식

서버 → 거의 빈 껍데기 HTML + JS 번들만 전송
        (<div id="root"></div> 이런 식으로 텅 비어있음)
브라우저 → JS를 다운로드하고 실행
         → JS가 데이터를 불러와서 그제서야 화면을 그림
         → 사용자는 그동안 빈 화면(또는 로딩 스피너)을 보게 됨

SSR — 지금 이야기하는 방식

서버 → 요청이 올 때마다 서버에서 미리 데이터까지 조회해서
        완성된 HTML(콘텐츠가 다 채워진 상태)을 만들어 전송
브라우저 → 받자마자 콘텐츠가 보이는 화면을 바로 그림
         → 이후 JS가 로드되면서 버튼 클릭 등 상호작용이 가능해짐
           (이 단계를 hydration(하이드레이션)이라고 부름)
핵심 특징

HTML이 완성된 채로 도착함

브라우저가 서버 응답을 받는 순간 이미 콘텐츠(텍스트, 이미지 등)가 채워진 HTML입니다. JS가 실행되기 전에도 콘텐츠 자체는 화면에 보입니다.

Hydration(하이드레이션) 과정이 필요

서버가 만들어준 정적인 HTML에, 브라우저에서 JS가 로드된 뒤 이벤트 리스너 등을 "붙여서" 실제로 클릭·입력이 가능한 상태로 만드는 과정입니다. 이 단계 전까지는 화면은 보이지만 버튼을 눌러도 반응이 없을 수 있습니다.

요청마다 서버에서 새로 렌더링

사용자가 요청할 때마다(또는 페이지 이동 시) 서버가 그 시점 기준으로 데이터를 조회해 HTML을 다시 만들어냅니다. (참고: 미리 만들어두고 캐싱하는 방식은 SSG(Static Site Generation)라고 구분해서 부릅니다.)
장점
초기 콘텐츠 표시가 빠름: JS 실행을 기다리지 않고 서버가 준 HTML을 바로 보여주므로, 특히 느린 네트워크·기기에서 체감 속도가 좋습니다.
SEO에 유리: 검색엔진 크롤러가 받는 첫 HTML에 이미 실제 콘텐츠가 다 들어있어서, 크롤러가 내용을 정확히 읽고 색인할 수 있습니다.
소셜 공유 미리보기 등에도 유리: 링크 공유 시 썸네일/제목 등을 긁어가는 크롤러도 콘텐츠를 정상적으로 읽을 수 있습니다.
단점
서버 부하 증가: 요청이 올 때마다 서버가 매번 HTML을 렌더링해야 하므로, 트래픽이 많으면 서버 자원을 더 많이 씁니다.
TTFB(첫 바이트까지 걸리는 시간) 증가 가능: 서버가 데이터 조회 + HTML 생성을 끝내야 응답을 보낼 수 있어서, 그 처리 시간만큼 응답이 늦어질 수 있습니다.
구현 복잡도 상승: 서버·클라이언트 양쪽에서 렌더링 로직을 다뤄야 하고, hydration 과정에서 서버와 클라이언트의 렌더링 결과가 어긋나는 "hydration mismatch" 같은 버그가 생기기도 합니다.
