코드 리뷰

먼저 실행 전 예상 → 실제 비교부터 해볼게요.

예상: '우유'를 지우면 그 체크박스도 같이 사라지고, 콘솔엔 unmount 우유가 찍힐 거라 기대하기 쉽습니다.

실제 결과

Q1. 체크는 어디에 있나? → 사라지지 않고 '빵'으로 옮겨갑니다. '우유'를 지웠는데 목록 맨 위(원래 '빵'이었던 자리)에 체크 표시가 그대로 남아있어요.

Q2. 콘솔에 새로 찍히는 줄은? → unmount 계란입니다. 지운 건 분명 '우유'인데, React 내부적으로는 목록 맨 아래의 '계란' 컴포넌트가 없어진 것으로 처리됩니다.

왜 이런 결과가 나올까? (원인 라인)
jsx
{items.map((it, index) => (
  <Row key={index} name={it.name} onDelete={() => 삭제(it.id)} />  // ← 바로 이 줄이 원인
))}

핵심은 React가 리스트의 각 항목을 구분하는 유일한 방법이 key뿐이라는 점입니다. React는 리렌더링할 때 "이전 렌더링의 어떤 요소가, 새 렌더링의 어떤 요소와 같은 것인가"를 판단해야 컴포넌트를 재사용할지 새로 만들지 정하는데, 그 판단 기준이 오직 key 값입니다.

지금 코드는 key={index}, 즉 배열 인덱스(0, 1, 2...)를 key로 쓰고 있어요. 문제는 인덱스는 "이 항목이 누구인지"가 아니라 "지금 몇 번째 자리에 있는지"만 나타낸다는 점입니다.

삭제 전:

index 0 (key=0) → 우유  (checked: true)
index 1 (key=1) → 빵    (checked: false)
index 2 (key=2) → 계란  (checked: false)

'우유'를 지우면 배열은 [빵, 계란]이 되고, map이 다시 인덱스를 매깁니다:

index 0 (key=0) → 빵   ← 원래 key=0 이었던 자리
index 1 (key=1) → 계란 ← 원래 key=1 이었던 자리
(key=2 는 더 이상 존재하지 않음)

React는 key=0이 렌더링 전후로 계속 존재하니까, "아, 이건 같은 컴포넌트구나"라고 착각하고 그 Row 인스턴스(그리고 그 안의 checked state)를 그대로 재사용합니다. 실제로는 그 안의 name만 '우유' → '빵'으로 바뀐 것뿐이에요. 그래서 체크 상태(state)는 사라지지 않고 새로운 이름표를 단 채 그대로 남는 겁니다. 반대로 key=2는 더 이상 매칭되는 자리가 없으니, React는 "이 컴포넌트는 사라졌다"고 판단해서 언마운트시키는데, 그게 하필 실제로 지운 '우유'가 아니라 맨 끝의 '계란'인 거예요.

해결 방법

인덱스 대신, 각 항목이 가진 고유하고 안정적인 값(여기서는 id)을 key로 써야 합니다.

jsx
{items.map((it) => (
  <Row key={it.id} name={it.name} onDelete={() => 삭제(it.id)} />
))}

이러면 '우유'(id: 1)를 지웠을 때 React는 key=1이 사라졌다는 걸 정확히 인식하고, 그 Row 컴포넌트만 정확히 언마운트합니다. '빵'(key=2)과 '계란'(key=3)은 key가 그대로 유지되니 각자의 state(체크 여부)도 그대로 보존됩니다.

한 걸음 더 — 왜 하필 "index를 key로 쓰지 마라"는 규칙이 유명한가

배열 끝에 추가/삭제만 하는 경우엔 index를 key로 써도 딱히 문제가 안 생깁니다. 인덱스와 항목의 대응 관계가 안 흔들리니까요. 하지만 지금처럼 중간이나 앞쪽 항목을 삭제·삽입·순서변경 하는 순간, 그 뒤에 있던 모든 항목의 인덱스가 한 칸씩 밀리면서 "React가 재사용해도 되는 컴포넌트"에 대한 판단이 완전히 틀어져 버립니다. 그래서 리스트를 렌더링할 때는 인덱스가 아니라, 데이터 자체가 가진 고유 id를 key로 쓰는 것이 React의 대표적인 베스트 프랙티스입니다.
