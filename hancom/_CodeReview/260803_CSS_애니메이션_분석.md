# CSS 애니메이션 성능 분석: A 코드 vs B 코드

**주제:** 애니메이션은 "무엇을 바꾸느냐"로 무거움/가벼움이 갈린다.

## 문제

A 코드와 B 코드는 화면 결과가 동일하다.

**A 코드**
```css
.box:hover {
  left: 30px;
  width: 300px;
}
```

**B 코드**
```css
.box:hover {
  transform: translateX(30px) scaleX(1.5);
}
```

**공통 기본 설정**
```css
.box {
  position: relative;
  left: 0;
  width: 200px;
  height: 100px;
  transform-origin: left center;
  transition: all 0.3s;
}
```

## Q1. 어느 쪽이 가벼운 코드일까?

**B 코드(transform)가 가볍다.**

## Q2. 왜 그 코드가 가벼울까?

브라우저가 화면을 렌더링하는 과정은 크게 세 단계로 진행된다.

1. **레이아웃(Layout / Reflow)** — 요소의 위치와 크기를 계산
2. **페인트(Paint)** — 픽셀을 실제로 그림
3. **합성(Composite)** — 그려진 레이어들을 화면에 합성

어떤 CSS 속성을 바꾸느냐에 따라 이 파이프라인 중 어디서부터 다시 계산해야 하는지가 달라진다.

### A 코드 — `left`, `width`

`left`와 `width`는 요소의 위치·크기, 즉 문서의 레이아웃에 직접 영향을 주는 속성이다. 값이 바뀔 때마다 브라우저는:

- 해당 요소뿐 아니라 주변 요소들의 레이아웃까지 다시 계산(Reflow)하고
- 다시 그리고(Repaint)
- 다시 합성한다

`transition: all 0.3s`로 0.3초 동안 매 프레임마다 이 전체 파이프라인이 반복되므로 비용이 크다.

### B 코드 — `transform`

`transform`(translateX, scaleX)은 레이아웃에 영향을 주지 않는 속성이다. 그래서 브라우저는 레이아웃과 페인트 단계를 건너뛰고 곧바로 합성 단계에서만 처리할 수 있다. 이미 그려진 레이어를 GPU가 이동·확대하는 것뿐이라 대부분 GPU 가속을 받아 훨씬 부드럽고 가볍게 동작한다.

> `opacity` 역시 같은 이유로 레이아웃·페인트를 건너뛸 수 있어 가벼운 속성에 속한다.

## 결론

- A는 **레이아웃부터 다시 계산해야 하는** 속성(`left`, `width`, `top`, `height` 등)을 건드리기 때문에 무겁다.
- B는 **합성 단계에서만 처리 가능한** 속성(`transform`, `opacity`)을 건드리기 때문에 가볍다.

실무에서 애니메이션 성능을 신경 쓸 때 `left/top/width/height` 대신 `transform`을, `visibility` 대신 `opacity`를 사용하라고 권장하는 이유가 바로 이것이다.
