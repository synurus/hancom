## 시나리오 ① 회의록을 놓치지 않고 남기고 싶은 순간

| 항목 | 내용 |
|---|---|
| **페르소나** | 김정현 — 방금 PT팀 논의를 마친 팀원 |
| **상황(트리거)** | PT 채널에서 박진과 기능 우선순위를 30분간 논의. 결론은 났지만 아무도 정리해 문서로 남기지 않음 |
| **행동** | 채널에 `@Hermes2 회의록 작성해줘 PT` 한 줄 입력. 채널 ID는 메시지에 자동 포함되어 별도 입력 불필요 |
| **시스템 처리** | ① `fetch_messages`로 최근 대화 수집 → ② `team-map.json`으로 참여자 실명(박진, 김정현) 매핑 → ③ 현재 주제 / 논의 내용 / 다음 목표 3단 구조로 본문 작성 → ④ git 안전장치 통과 후 GitHub `회의록/` 폴더에 커밋·푸시 |
| **결과** | 참여자 전원이 완료 즉시 `@멘션`으로 알림을 받고, `2026-07-29_PT_2차_회의록.md`가 저장소에 확정됨 |
| **가치** | 논의가 끝난 그 순간의 맥락이 사라지기 전에, 사람이 다시 읽고 요약할 필요 없이 문서로 고정됨 |

**대화 흐름**

```
김정현  1:59 PM
@Hermes2 회의록 작성해줘 PT

Hermes2 [APP]  2:01 PM
@박진 @김정현 회의록 작성 완료했어요 📝
2026-07-29_PT_2차_회의록.md
→ github.com/Scalmia/TeamB/blob/main/회의록/2026-07-29_PT_2차_회의록.md
```

## 시나리오 ② 잠깐 자리를 비운 사이의 논의를 따라잡고 싶을 때

| 항목 | 내용 |
|---|---|
| **페르소나** | 김정현 — 다른 팀원(이현우)의 채널 논의를 확인해야 하는 팀원 |
| **상황(트리거)** | 이현우 채널에서 새 기획안 관련 논의가 오갔지만, 메시지가 많아 처음부터 다시 읽기엔 부담스러움 |
| **행동** | 해당 채널에 `@Hermes2 여기 요약해줘` 요청 — 회의록과 달리 파일 저장 없이 즉시 답장만 받으면 되는 상황 |
| **시스템 처리** | 최근 대화를 화자별로 정리하고, Discord 마크다운(볼드·불릿·구분선)으로 가독성 있게 구성한 뒤 결론까지 붙여 그 자리에 바로 답장 |
| **결과** | 회의에 직접 참여하지 않았어도 30초 만에 핵심 논의와 결론을 파악하고, 다음 회의에 바로 참여 가능한 상태가 됨 |
| **가치** | "다시 읽기" 대신 "결론만 확인"으로 대화 추적 비용을 없앰. 저장소에 남기지 않아도 되는 가벼운 확인 용도에 최적화 |

**대화 흐름**

```
김정현  3:29 PM
@Hermes2 여기 요약해줘

Hermes2 [APP]  3:30 PM
이현우
· "봇 프롬프팅 아레나" 신규 기획안 제안
· 4주 일정, 4인 역할 구조 제시
· 리스크: DSL 폭이 좁으면 프롬프트 차이가 승률에 안 드러날 수 있음
---
결론: 5번째 기획안 검토 필요 · 오늘 목표 "기획안 1개 선정" 포함 여부 논의 필요
```

## 시나리오 ③ 새 채널을 만들자마자 봇이 바로 반응하는 순간

| 항목 | 내용 |
|---|---|
| **페르소나** | 박진 — 새로운 하위 프로젝트를 위해 채널을 새로 만든 팀원 |
| **상황(트리거)** | 팀 서버에 `#새-프로젝트` 채널을 새로 개설. 기존 방식이라면 봇 접근 권한을 팀원이 수동으로 다시 등록해야 하는 상황 |
| **행동** | 별도 설정 없이 새 채널에서 바로 `@Hermes2 여기 요약해줘` 또는 회의록 작성을 요청 |
| **시스템 처리** | 접근 검증 로직이 채널 단위(`groups`) 등록 여부를 먼저 확인 → 등록이 없어도 채널이 속한 서버가 `guilds`에 등록되어 있으면 **자동 허용(폴백)** → 스레드는 부모 채널 정책을 상속받아 함께 커버됨 |
| **결과** | 팀원이 어떤 채널·스레드를 새로 만들어도 봇이 등록 절차 없이 즉시 반응함 |
| **가치** | "새 채널이 생길 때마다 수동 등록" 이라는 운영 부담이 완전히 사라짐. 팀 구조가 계속 바뀌는 프로젝트 환경에 맞는 확장성 확보 |

## 시나리오 ④ 예상과 다른 상황에서 시스템이 스스로 멈추는 순간

| 항목 | 내용 |
|---|---|
| **페르소나** | 김정현 — 회의록 작성을 요청한 팀원 |
| **상황(트리거)** | 마침 다른 팀원이 같은 저장소에 아직 커밋되지 않은 작업물을 남겨둔 상태이거나, 원격 저장소에 새로운 커밋이 먼저 반영되어 충돌 가능성이 있는 상황 |
| **행동** | 평소와 동일하게 `@Hermes2 회의록 작성해줘 PT` 요청 |
| **시스템 처리** | git 안전장치가 순서대로 확인 — ① 새 회의록 파일 외 다른 변경 사항 존재 여부 ② `main` 브랜치 여부 ③ 최신 이력 pull 시 충돌 여부 ④ 새 파일 1개만 선택적 반영 ⑤ push 거부/실패 여부. 하나라도 예상과 다르면 즉시 중단 |
| **결과** | 회의록 파일 생성 자체는 완료되지만 저장소에는 반영되지 않고, 정확한 중단 사유와 함께 사람에게 보고됨 (다른 팀원의 작업물을 임의로 덮어쓰거나 강제 push하지 않음) |
| **가치** | "정상 상황에서는 끝까지 자동으로, 조금이라도 예상과 다르면 반드시 멈추고 사람에게 알린다"는 설계 원칙이 실제로 작동함을 보여줌 — 자동화가 신뢰할 수 있는 이유 |

|---|---|---|---|---|
| 트리거 | 논의 종료 후 기록 필요 | 논의를 놓쳐 따라잡기 필요 | 새 채널/스레드 개설 | 저장소 상태 이상 |

| 보여주는 가치 | 기록의 자동화 | 탐색 비용 제거 | 운영 확장성 | 자동화의 신뢰성 |
