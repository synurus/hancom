# cleanflow — 유저 시나리오

> **cleanflow 를 쓰는 사람**의 이야기다. ZETEO 를 플레이하는 사람이 아니다.
> 사용자는 TeamB 팀원 넷이고, 쓰는 곳은 디스코드다.

---

## 등장인물

| | 파트 | 이 시스템에서의 역할 |
|---|---|---|
| 유민성 | 서버 · DB | 요청자 · 파일 소유자 |
| 김정현 | 봇 | 요청자 · 파일 소유자 |
| 이현우 | 게임 화면 | 요청자 · 파일 소유자 |
| 박진 | 공통 화면 | 요청자 · 파일 소유자 |

**요청자와 소유자가 같을 수도 다를 수도 있다.** 그 차이가 시나리오를 가른다.

---

## 시나리오 1 — 내 파일을 내가 정리한다 (가장 흔한 경우)

**상황** 민성님이 `index.ts`(662줄)를 계속 고치는데, 함수를 찾을 때마다 파일을 위아래로 훑고 있다.

```
민성  디스코드 #cleanflow 채널에 한 줄

      apps/backend/src/index.ts

cleanflow
      최신 확인 → 브랜치 → 정의 → 판정 → 구역 → 커밋 2개 → PR

      🧹 apps/backend/src/index.ts 정리했습니다 — PR #24

      동작은 안 바뀝니다. tsc 통과했습니다.
      커밋 1(이동)만 보시면 안전 확인은 끝납니다.

      구역 5개로 나눴습니다
        1. 서버가 켜진다      2. 방에 들어온다
        3. 판이 돈다          4. 봇 차례를 만든다
        5. 판이 끝나고 적재한다

      ⚠️ 추정으로 쓴 주석 3개 (※ 표시) — 확인 부탁드립니다

민성  PR 열어봄
      커밋 1 diff — 이동만인 게 보인다. OK
      커밋 2 — ※ 표시 3개 중 2개는 맞고, 1개는 틀림

      "3번 주석은 아니에요. 재연결 때문이 아니라 타이머 정합성 때문입니다"

cleanflow
      해당 주석 수정 → 같은 PR 에 커밋 추가

민성  머지
```

**핵심** — 소유자가 고쳐주는 지점이 딱 하나, **추정 주석**뿐이다. 배치는 논쟁거리로 만들지 않는다.

## 시나리오 2 — 아무것도 하지 않고 끝난다

**상황** 현우님이 `hooks/useGameState.ts`(48줄)를 지목한다.

```
현우  apps/frontend/src/hooks/useGameState.ts

cleanflow
      판정 4문항을 돌린다
        □ 스크롤 없이 윤곽이 잡히나          → 잡힌다
        □ 선언을 찾을 때 훑어야 하나          → 아니다
        □ 책임을 한 문장으로 말할 수 있나     → 있다
        ☑ 안 드러난 이유가 있나              → 있다 (하나만 걸림)

      이 파일은 배치는 손댈 게 없습니다.
      구분선을 넣으면 48줄에 선이 더 많아집니다.

      다만 파일 머리 주석 하나만 제안드립니다 — PR #25
      (소켓 생명주기를 이 훅 하나가 쥐는 이유)
```

**핵심** — **"이 파일은 됐다"가 정상 결과다.** 규칙이 모든 파일을 뜯어고치라고 하면 그건 취향이지 규칙이 아니다.

## 시나리오 3 — 남의 파일을 정리한다 (통보)

**상황** 정현이 봇 작업 중에 `view.ts`(민성님 소유)를 읽다가 계속 헤맨다.

```
정현  apps/backend/src/view.ts

cleanflow
      최신 확인 — 미병합 브랜치에 변경 없음
      정리 → PR #26

      소유자가 민성님이므로 #유민성-logs 에 통보

      🧹 apps/backend/src/view.ts 정리했습니다 — PR #26

      동작은 안 바뀝니다. tsc 통과했습니다.

      이 파일 지금 만지고 계시면 이렇게 받으시면 됩니다.
        · 아직 시작 전    → PR 머지하고 그 위에서 작업
        · 이미 고치는 중  → git stash → PR 머지 → git stash pop
        · 많이 고치셨으면 → 머지하지 마시고 알려주세요

      ⚠️ 추정으로 쓴 주석 2개 — 확인 부탁드립니다
```

**핵심** — **"작업 중이세요?"라고 묻지 않는다.** 물어보면 답을 기다리는 동안 진도가 멈춘다. 바꿨다고 알리고 **받아 쓰는 법**을 준다.

## 시나리오 4 — 겹쳤다

**상황** 시나리오 3에서, 민성님이 마침 `view.ts`를 크게 고치는 중이었다.

```
민성  "그거 지금 반쯤 갈아엎는 중이라 머지하면 충돌 나요"

cleanflow
      PR 을 닫는다. 브랜치도 지운다.

      알겠습니다. 민성님 작업이 dev 에 들어간 뒤에 다시 돌리겠습니다.
      정리 자체는 5분이면 다시 됩니다.

      (며칠 뒤, 민성님 작업 머지 완료)

정현  apps/backend/src/view.ts

cleanflow
      최신 코드 기준으로 다시 정리 → PR #31
```

**핵심** — **버리는 비용이 싸다.** 정리는 재실행이 쉬우므로 겹치면 그냥 버리고 나중에 다시 한다. 이 성질 덕분에 "허락 없이 먼저 하기"가 감당 가능한 선택이 된다.

> 이 시나리오는 가정이 아니다. 2026-08-20 `room.ts`에서 실제로 일어났고, PR #22 를 닫았다.

## 시나리오 5 — 정리가 구조 문제를 찾아낸다

**상황** 정현이 `bot/index.ts`(501줄)를 지목한다.

```
cleanflow
      ② 기획 단계 — 구역을 나누는데 두 함수가 어디에도 안 들어간다

      🧹 apps/backend/src/bot/index.ts 정리했습니다 — PR #27

      구역 6개로 나눴습니다.

      📌 정리하면서 드러난 것 2건
        · LABEL_POOL·assignLabel 이 joinRoom 근처에 있었는데
          실제로 쓰는 건 assignLabels(판 시작)뿐입니다
        · 발화 검사가 speak() 와 chatOrSilent() 두 군데로 나뉘어 있어
          어느 구역에도 온전히 안 들어갑니다 — 책임이 둘일 수 있습니다

      두 번째는 이 PR 범위 밖이라 손대지 않았습니다. 판단 부탁드립니다.
```

**핵심** — **순서 정리는 목적이 아니라 탐지 도구다.** *"이걸 어디 놓지?"*가 답이 안 나오는 함수가 곧 구조 문제다. 다만 cleanflow 는 **찾아서 보고만 하고 고치지 않는다** — 그건 사람이 판단할 일이다.

## 시나리오 6 — ④ 활용, 한 바퀴가 닫힌다

**상황** PR #24 머지 후, 민성님이 `index.ts`에 새 기능을 넣는다.

```
민성  방 목록 조회 기능을 추가해야 한다

      정리된 파일을 연다 → 파일 머리에 구역 목록이 있다
        1. 서버가 켜진다   2. 방에 들어온다   3. 판이 돈다  ...

      "방에 들어온다" 구역에 넣으면 되겠네

      → 넣을 자리를 찾느라 훑지 않았다

민성  #cleanflow 채널에 한 줄

      "index.ts 에 방 목록 추가했는데 자리 고민 안 했습니다"

cleanflow
      TeamB/4주차/정리기록/backend-index.md 에 이 결과를 덧붙인다
```

**핵심** — **여기까지가 한 바퀴다.** 정리해놓고 안 써보면 그 배치가 쓸 만한지 알 수 없다. *"새 코드를 넣을 자리가 자명했는가"*가 이 시스템의 최종 평가 기준이다.

반대로 **자리가 애매했다면 구역 이름이 잘못된 것**이고, 그때는 이름을 다시 짓는다.
