# cleanflow — 코드에 읽는 순서를 만드는 시스템

> 4주차 평가 항목 **클린 코드**에 대한 우리 팀의 답.

---

## 1. 문제 — 파일은 읽는 순서가 아니라 쓴 순서로 남는다

파일은 만들어진 뒤에도 계속 자란다. 새 기능은 대개 **파일 끝에 붙는다.** 이미 있는 코드를 헤집는 것보다 그게 안전하고 빠르기 때문이다.

그래서 시간이 지나면 파일의 순서는 이렇게 된다.

```
읽는 순서   이 파일이 무엇을 하는가 → 어떻게 하는가 → 세부
쓴 순서     처음 만든 것 → 그다음 붙인 것 → 어제 붙인 것
```

**둘은 거의 겹치지 않는다.** 그리고 이건 누가 게을러서 생긴 결과가 아니다. 아무도 한 줄 추가할 때마다 파일 전체를 재배치하지 않는다. **아무것도 안 해도 저절로 벌어지는 일**이라, 의식적으로 되돌리지 않으면 계속 나빠지기만 한다.

### 지금 우리 코드에서 (2026-08-20 시점 관찰)

이 관찰은 **규칙의 근거가 아니라 문제의 증거**다. 코드는 계속 바뀌므로 아래 예시는 곧 낡는다.

| 파일 | 증상 |
|---|---|
| `bot/index.ts` | 진입점이 파일 맨 끝에 있는 건 맞는 배치인데, **그 앞이 정리돼 있지 않다.** 서로 부르지 않는 함수가 붙어 있고, 부르는 함수는 떨어져 있다 |
| 〃 | 상수 60줄이 성격 구분 없이 파일 앞에 몰려 있다. 무슨 값인지 모른 채 읽게 된다 |
| 〃 | 발화 검사가 두 군데로 나뉘어 있어 "어떤 검사를 어디서 하는지"가 한눈에 안 잡힌다 |
| `hooks/useGameState.ts` | **반대 경우.** 짧고 순서도 맞는데, 왜 이 방식인지가 안 적혀 있다 |

마지막 줄이 중요하다. **큰 파일과 작은 파일은 다른 이유로 안 읽힌다.**

---

## 2. 왜 린터로는 안 되는가

우리는 이미 Prettier와 ESLint를 쓴다. 그런데도 위 문제가 남아 있다.

| | 린터 | 우리 문제 |
|---|---|---|
| 단위 | **줄** — 세미콜론, 안 쓰는 변수, 들여쓰기 | **파일** — 무엇이 어디에 있는가 |
| 판단 | 규칙 위반인가 | 사람이 읽을 수 있는가 |
| 못 하는 것 | — | **왜 이렇게 짰는지**는 코드 어디에도 없다 |

모든 줄이 규칙을 지켜도 순서가 뒤죽박죽이면 못 읽는다. 반대로 순서가 완벽해도 *"왜 하필 이 방식인가"*는 코드만 봐서는 영영 알 수 없다. **둘 다 린터의 사정거리 밖이다.**

## 3. 정의 — 우리에게 클린 코드란

> **처음 읽는 사람이 위에서 아래로 한 번 훑어서 이해할 수 있는 코드.**

이 정의를 고른 이유는 그것이 **확인 가능**하기 때문이다. "좋은 코드"나 "유지보수하기 쉬운 코드"는 판정할 방법이 없지만, 위 문장은 사람 하나를 앉혀놓고 시켜보면 바로 답이 나온다.

여기서 두 가지 조건이 나온다.

```
① 순서가 흐름을 따를 것                    → 읽다가 되돌아가지 않아도 된다
② 흐름만으로 알 수 없는 것이 적혀 있을 것   → 왜 이 방식인지
```

①은 배치의 문제, ②는 주석의 문제다. **둘은 한 몸이다** — ①은 한 번 정리하면 끝나지만, 규칙이 눈에 안 보이면 다음 사람이 또 끝에 붙인다. ②의 구분선이 ①을 **눈에 보이게 고정**해서 그걸 막는다.

## 4. 배치 규칙

### 4-1. 조립식 — 재료가 먼저, 완성품이 마지막

**작은 것부터 쌓아 올려 마지막에 조립한다.** 진입점은 파일 맨 끝에 둔다.

```
파일 머리   이 파일이 무엇을 책임지는가 (+ 큰 파일이면 구역 목록)
    ↓
   재료     각 구역의 함수와 상수
    ↓
  진입점    위의 것들을 조립해 밖으로 내보내는 것
```

**이유** — 우리는 함수마다 주석을 붙인다. 그래서 위에서부터 읽으면 재료 하나하나가 무엇인지 알게 되고, 마지막 조립을 읽을 때는 이미 부품을 다 아는 상태다. 진입점을 먼저 보면 모르는 이름이 잔뜩 나와 결국 아래로 내려갔다 올라와야 한다.

이건 새로 만드는 규칙이 아니라 **이미 잘 읽히는 파일의 배치**다. `bot/llm.ts`가 정확히 이 모양이고(준비 → 두 갈래 → 마지막에 `generate`), 그래서 읽힌다.

> **큰 파일에서는 파일 머리의 구역 목록이 필수다.** 조립식은 "마지막까지 가야 전체가 보인다"는 약점이 있는데, 머리의 지도가 그걸 메운다.

### 4-2. 구역 이름은 게임에서 딴다

> **이 코드가 게임의 어느 순간에 작동하는가**로 이름을 짓는다.

기술 용어(`유틸`, `헬퍼`, `상태관리`)로 부르면 아무 프로젝트에나 붙는 이름이 되고, 그러면 새 함수를 어디 넣을지 또 애매해진다. 실제 플레이에서 벌어지는 일로 부르면 **넣을 자리가 자명해진다.**

**구역은 3~5개를 넘지 않게 크게 나눈다.** 잘게 쪼개면 구분선이 많아져서 지도 역할을 못 한다.

게임과 무관한 기반 코드(DB 접속, 소켓 설정 등)에는 이 규칙이 안 통한다. **그때만 역할로 짓는다.**

**예시** — `bot/index.ts`에 적용하면

```
── 말할지 정한다        발언 확률 상수 · shouldWaitForOthers · chatOrSilent
── 말을 만든다          speak · generateOrEmpty · 검사류 · fallbackLine
── 사람처럼 내보낸다     지연 3종 · 문장 분할 · 라벨 처리
── 누구를 찍을까        bandwagonTarget · clearLeader
── 방이 기억하는 것      roomKey · takePendingTail · recallTarget · carryTarget
── 진입점               decideBotAction
```

**상수를 각자 쓰이는 구역 안으로 흩어놓는 것이 핵심**이다. `CHAT_BEFORE_VOTE_CHANCE`가 「말할지 정한다」 안에 있으면 그 자리에서 뜻이 통한다.

### 4-3. 판정은 크기가 아니라 증상으로

**줄 수로 기준을 못 박지 않는다.** 지금 코드에 맞춘 숫자는 코드가 자라면 곧 낡고, 같은 줄 수여도 함수가 3개인 파일과 20개인 파일은 전혀 다르다.

대신 이렇게 묻는다.

```
□ 스크롤 없이 파일의 윤곽이 잡히는가
□ 선언 하나를 찾을 때 파일을 훑어야 하는가
□ 이 파일이 무엇을 책임지는지 한 문장으로 말할 수 있는가
□ 그렇게 만든 이유 중 코드에 안 드러나는 것이 있는가
```

앞 둘이 걸리면 **구역 나누기와 지도**가 필요하고, 뒤 둘이 걸리면 **머리 주석**이 필요하다. 둘 다 걸릴 수도, 하나도 안 걸릴 수도 있다.

### 가장 중요한 원칙

> **규칙은 "고쳐라"보다 "이 파일은 됐다"를 더 자주 말할 수 있어야 한다.**

이미 잘 쓰인 파일을 규칙이 뜯어고치라고 하면, 그건 규칙이 아니라 취향이다. 좋은 규칙이라면 **막히는 파일에만 걸리고 나머지는 통과**시켜야 한다.

## 5. 파이프라인 — 정의 → 기획 → 개발 → 활용

파일 하나를 다룰 때 네 단계를 거친다. **순서를 건너뛰지 않는 것이 핵심**이다. 특히 1단계 없이 바로 함수를 옮기기 시작하면 무엇을 기준으로 옮기는지가 없어서 취향 싸움이 된다.

### ① 정의 — 이 파일은 무엇을 책임지는가

코드를 건드리기 전에 **말로 먼저 정한다.**

```
· 이 파일이 책임지는 것 한 문장
· 이 파일을 읽는 사람이 알고 싶어 할 것
· 코드에 안 드러나는 결정 (왜 이 방식인가)
```

한 문장으로 안 써지면 그것 자체가 결과다 — **책임이 두 개 이상**이라는 뜻이고, 배치를 아무리 바꿔도 안 읽힌다.

### ② 기획 — 어떤 순서가 나와야 하는가

정의에 따라 배치 계획을 세운다. 실제 코드는 아직 안 건드린다.

```
· 호출 관계를 훑어 구역 후보를 뽑는다
· 게임의 어느 순간인지로 구역 이름을 붙인다 (3~5개)
· 상수·타입을 쓰이는 구역으로 배정한다
· 어느 구역에도 안 들어가는 선언을 표시한다   ← 책임이 두 개라는 신호
```

마지막 줄이 이 단계의 진짜 수확이다. **순서 정리는 그 자체가 목적이라기보다 구조 문제를 드러내는 탐지 도구**로 더 값지다.

### ③ 개발 — 옮기고 적는다

**커밋을 둘로 나눈다.** 섞으면 리뷰가 불가능해진다.

```
커밋 1  이동만    선언을 재배치하고 구분선을 넣는다
                  함수 본문은 한 글자도 바꾸지 않는다
커밋 2  주석만    파일 머리와 각 구역·함수에 설명을 적는다
```

커밋 1을 "본문 불변"으로 못 박으면 **동작이 안 바뀌었다는 걸 diff로 확인할 수 있다.** 삭제된 줄과 추가된 줄이 정확히 짝이 맞으면 그게 증거다.

`npx tsc -b --noEmit`과 빌드 통과는 두 커밋 모두에서 확인한다.

### ④ 활용 — 쓰고, 유지되는지 본다

```
· 정리된 파일로 실제 작업을 해본다 (버그 수정이든 기능 추가든)
· 새 코드를 넣을 자리가 자명한가 — 아니면 구역 이름이 잘못된 것
· 다른 사람이 읽고 막히는 지점이 남았는지 확인
```

**여기까지 해야 한 바퀴다.** 정리해놓고 안 써보면 그 배치가 실제로 쓸 만한지 알 수 없다.

## 6. 운영 — 요청부터 반영까지

3주차 코드북과 같은 방식이다. **디스코드에 파일 경로를 남기면** 시작된다.

```
① 요청     팀원이 디스코드 채널에 경로를 남긴다
             예: apps/backend/src/bot/index.ts

② 정리     cleanflow 가 파이프라인 ①~③ 을 수행한다
             전용 브랜치를 파고, 커밋 2개로 나눠 올린다

③ PR       PR 을 연다. 본문에 이렇게 담는다
             · 이 파일이 무엇을 책임지는가 (① 정의의 결과)
             · 무엇이 어디로 갔는지 표
             · 어느 구역에도 안 들어간 선언 = 구조 문제 후보
             · tsc · 빌드 통과 여부

④ 통보     소유자에게 "바꿨으니 받아 쓰세요" 라고 알린다
             허락을 구하지 않는다 — 물어보면 진도가 안 나간다
```

**허락이 아니라 통보인 이유** — "이 파일 지금 만지고 계세요?" 를 매번 물으면 답을 기다리는 동안 아무것도 못 한다. 그리고 대부분은 안 겹친다. 그래서 **먼저 바꾸고, 받아 쓰는 법을 함께 알린다.**

```
· 아직 시작 전    → PR 머지하고 그 위에서 작업
· 이미 고치는 중  → git stash → PR 머지 → git stash pop
· 많이 고쳤으면   → 머지하지 말고 알려달라. 그쪽 작업이 끝난 뒤 다시 돌린다
```

**다만 주석만은 확인을 받는다.** 배치는 틀려도 읽기 불편할 뿐이지만, **틀린 주석은 없는 주석보다 나쁘다.** 그래서 추정으로 쓴 주석에는 `※ 소유자 확인 필요` 표시를 붙여 따로 뽑아 보낸다.

### 왜 PR로 하는가

- **재배치는 diff가 크다.** GitHub이 순수 이동을 잘 못 보여주므로, PR 본문의 "무엇이 어디로" 표가 diff를 대신 읽어준다
- **파일 소유자가 판단할 자리가 생긴다.** 구역 이름은 그 코드를 만든 사람이 제일 잘 짓는다
- **PR 자체가 산출물이 된다.** 리뷰 대화가 남아서, 3주차 코드북처럼 나중에 읽을 기록이 된다

### 겹치면 어떻게 되나

같은 파일을 누가 동시에 고치고 있으면 충돌한다. **완전히 막을 수는 없다.**

| | 감지되나 | 어떻게 |
|---|---|---|
| 남이 **푸시한** 작업 | ✅ | 미병합 브랜치의 해당 파일 diff 를 먼저 확인한다 |
| 남의 **로컬** 작업 | ❌ | git 이 알 방법이 없다 |

로컬 작업은 통보로만 메울 수 있다. 그래서 ④가 필요하다.

**제일 확실한 완화책은 시기다.** 다들 버그를 고치는 중인 지금이 겹칠 확률이 가장 높으므로, **바닥 다지기가 끝나고 dev 에 머지된 뒤에** 본격적으로 돌린다.

---

## 7. 시스템 — 스킬로 만든다

`/cleanflow <파일경로>` — 파이프라인 ①~③을 수행하고 PR까지 연다. ④는 사람이 한다.

### 스킬이 보는 신호

절대 기준이 아니라 **파일 안에서의 상대적 관계**를 본다. 그래야 코드가 자라도 기준이 안 낡는다.

| 신호 | 무엇을 말해주나 |
|---|---|
| 선언 개수와 밀도 | 구역 나누기가 필요한가 |
| `export` 개수 | 책임이 몇 개인가 |
| 상수 선언과 실제 사용처의 거리 | 값이 뜻을 잃은 채 앞에 몰려 있는가 |
| 호출 관계 vs 배치 순서 | 흐름과 순서가 어긋나는가 |
| 파일 머리 주석 유무 | 짧은 파일에서 유일하게 중요한 것 |
| 어느 구역에도 안 들어가는 선언 | 책임이 두 개라는 신호 |

**큰 파일과 작은 파일에 같은 규칙을 적용하되, 걸리는 신호가 다르다.** 처방이 달라지는 것이지 규칙이 두 개인 것이 아니다.

### 처방하지 않는 경우

신호가 하나도 안 걸리면 **"이 파일은 됐다"로 끝낸다.** PR도 열지 않고 그렇게 답한다. 억지로 구분선을 넣지 않는다.

```
4주차/
  시스템/       기획 · 시스템 설계도 · 유저 시나리오 · 와이어프레임 · 시연 영상 · 발표자료
  정리기록/     파일마다 하나씩 — 정의 · 구역 · PR 링크 · 드러난 구조 문제
```

3주차의 `코드북/`과 같은 구조다. **시스템만 만들고 끝내지 않고, 그것으로 실제 코드를 정리한 기록이 남는다.**

마침 기획서 v4.0의 **§3 바닥 다지기**가 주석·최적화를 다루고 있어, 이번 주차 과제와 실제 작업이 그대로 맞물린다. 과제용으로 따로 만드는 것이 아니라 **하던 일을 방법으로 정리하는 것**이다.
