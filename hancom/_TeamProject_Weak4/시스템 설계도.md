# cleanflow — 시스템 설계도

> 4주차 클린 코드 시스템. 무엇이 무엇을 부르고, 어디서 멈추는가.

---

## 1. 전체 그림

```
  ┌─ 사람 ──────────┐        ┌─ cleanflow ────────────────┐       ┌─ 저장소 ────────┐
  │                 │        │                            │       │                 │
  │  디스코드에      │ 경로   │  ① 정의   책임 한 문장      │ 커밋  │  Zeteo          │
  │  파일 경로를     ├───────▶│  ② 기획   구역 나누기       ├──────▶│  chore/ 브랜치   │
  │  남긴다          │        │  ③ 개발   재배치 + 주석     │       │                 │
  │                 │        │                            │  PR   │                 │
  └─────────────────┘        │      ↓ 판정에서 멈출 수 있음 │──────▶│  PR #N          │
           ▲                 └────────────┬───────────────┘       │                 │
           │                              │                       │  TeamB          │
           │        통보 (-logs 채널)      │                       │  4주차/정리기록/  │
           └──────────────────────────────┘                       └─────────────────┘
                                          │
                                  ④ 활용은 사람이 한다
                                  (정리된 파일로 실제 작업 → 자리가 자명한지 확인)
```

**자동으로 `dev`에 들어가지 않는다.** cleanflow는 PR을 여는 데까지만 하고, 머지는 사람이 한다.

---

## 2. 입력과 출력

| | |
|---|---|
| **입력** | 파일 경로 하나 (`apps/backend/src/room.ts` 또는 `room.ts`) |
| **출력 1** | `chore/cleanflow-<파일명>` 브랜치 — 커밋 두 개 |
| **출력 2** | PR — 무엇이 어디로 갔는지 + 드러난 문제 + 확인 필요한 주석 |
| **출력 3** | `TeamB/4주차/정리기록/<파일명>.md` |
| **출력 4** | 소유자 `-logs` 채널 통보 |

**"무엇이 문제인지"는 입력받지 않는다.** 판정을 시스템이 한다.

## 3. 처리 흐름 — 멈추는 지점이 셋

```
        시작
          │
          ▼
   ┌──────────────┐
   │ 최신인지 확인 │  git fetch → dev 와 diff → 미병합 브랜치 확인
   └──────┬───────┘
          │  미병합 변경 있음
          ├──────────────────────────▶  ✋ 멈춤 ①  "그거 먼저 머지해주세요"
          │
          ▼
   ┌──────────────┐
   │  ① 정의       │  책임 한 문장 · 호출 관계 조사
   └──────┬───────┘
          │  한 문장으로 안 써짐
          ├──────────────────────────▶  ⚠️ 계속하되 PR 에 적는다 (책임이 둘)
          ▼
   ┌──────────────┐
   │  판정 4문항   │  □ 윤곽이 잡히나  □ 훑어야 찾나
   └──────┬───────┘  □ 한 문장으로 되나 □ 안 드러난 이유가 있나
          │  하나도 안 걸림
          ├──────────────────────────▶  ✋ 멈춤 ②  "이 파일은 됐습니다"
          │
          ▼
   ┌──────────────┐
   │  ② 기획       │  구역 3~5개 · 게임에서 이름 따기
   └──────┬───────┘
          ▼
   ┌──────────────┐
   │ 커밋 1 이동만 │──▶ 검증: 구분선 뺀 줄이 정렬 후 동일한가
   └──────┬───────┘         │ 아니면
          │                 └────────▶  ✋ 멈춤 ③  커밋하지 않는다
          ▼
   ┌──────────────┐
   │ 커밋 2 주석만 │──▶ 검증: diff 의 모든 변경 줄이 주석인가
   └──────┬───────┘
          ▼
   ┌──────────────┐
   │  타입 검사    │  npx tsc --noEmit
   └──────┬───────┘
          ▼
       PR + 통보 + 기록
```

**멈춤 ②가 이 시스템의 성격을 정한다.** 아무것도 안 하고 끝나는 것이 정상 결과 중 하나다.

## 4. 커밋을 둘로 쪼개는 구조

리뷰어가 **커밋 1만 보면 안전 확인이 끝나도록** 설계했다.

```
커밋 1  이동만                    커밋 2  주석만
────────────────────────         ────────────────────────
선언 재배치                       파일 머리 (책임 + 구역 지도)
구역 구분선 삽입                   각 결정의 "왜"
기존 주석은 딸려서 이동            추정에는 ※ 표시

함수 본문 변경 0                   코드 변경 0
```

### 검증이 자동인 이유

| 커밋 | 무엇을 보증하나 | 어떻게 |
|---|---|---|
| 1 | 동작이 안 바뀜 | 구분선 뺀 줄들을 **정렬**해서 이전과 비교. 순서만 바뀌었으면 일치한다 |
| 2 | 코드가 안 바뀜 | diff 의 `+`/`-` 줄이 **전부 주석**인지 확인 |

테스트가 없는 저장소라, **diff 자체를 증거로 쓰는 것**이 유일하게 쓸 만한 방법이다.

## 5. 겹침을 다루는 구조

```
                    같은 파일을 누가 고치고 있나?
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
      푸시된 작업                       로컬 작업
      (다른 브랜치에 있음)               (남의 PC 안에만 있음)
              │                               │
              ▼                               ▼
      git 으로 감지 가능                git 이 알 수 없음
      → 멈춤 ① 로 차단                  → 막을 방법이 없다
                                              │
                                              ▼
                                    ④ 통보로 메운다
                                    "바꿨습니다. 받아 쓰는 법은 —"
```

**허락을 구하지 않는다.** 물어보면 답을 기다리는 동안 진도가 멈추고, 대부분은 안 겹친다.
대신 통보에 **받아 쓰는 법 세 가지**를 같이 적는다.

```
아직 시작 전    → PR 머지하고 그 위에서 작업
이미 고치는 중  → git stash → PR 머지 → git stash pop
많이 고쳤으면   → 머지하지 말고 알려달라. 끝난 뒤 다시 돌린다
```

## 6. 주석의 두 갈래 — 이 시스템의 유일한 확인 절차

배치는 틀려도 읽기 불편할 뿐이다. 그런데 **틀린 주석은 없는 주석보다 나쁘다.** 읽는 사람이 그걸 믿기 때문이다.

```
      "왜 이렇게 짰나" 를 적을 때
                │
        ┌───────┴────────┐
        ▼                ▼
   코드·주석·기획서     내가 판단한 것
   에서 읽어낸 것
        │                │
        ▼                ▼
     그냥 적는다      ※ 소유자 확인 필요
                          │
                          ▼
                   PR 본문에 따로 뽑아
                   통보에도 명시한다
```

LLM은 그럴듯한 이유를 만들어내는 데 능하다. **이 갈림길이 그것을 거르는 유일한 장치다.**

## 7. 다른 시스템과의 관계

| 시스템 | 하는 일 | 이 시스템과의 차이 |
|---|---|---|
| ESLint · Prettier | **줄** 단위 규칙 | cleanflow 는 **파일** 단위 배치를 본다. 겹치지 않는다 |
| 3주차 `/codebook` | 코드를 **읽는 법**을 만든다 | cleanflow 는 코드 **자체**를 읽히게 바꾼다 |
| 기획서 v4.0 §3 | 바닥 다지기 (버그·주석·최적화) | cleanflow 가 그중 **주석 항목의 실행 도구**다 |

`/codebook`과는 **반대 방향**이다. 코드북은 어려운 코드를 그대로 두고 안내서를 만들고, cleanflow는 안내서가 덜 필요하도록 코드를 바꾼다. **둘 다 필요하다** — 바꿀 수 없는 복잡함은 코드북이 맡는다.
